1.1 项目定位

BLM Agent 是 BLM 业务建模工具的内置 AI 助手。遵循 Harness = Model + Tools + Knowledge + Permissions 的架构哲学——模型提供智能（Agency comes from training），Harness 提供执行环境。

Harness 要素实现
工具bash, read_file, write_file, edit_file, grep, glob, ls, web_fetch + 5 BLM 专用 + 2 元工具
知识SKILL.md 两层加载（索引→完整内容）、种子技能库（5个）、8层文件式提示词
感知BLM 工作区读写、16 种类型化事件流、工具结果分析
行动双层 Agent 循环（follow-up/steering）、工具调度（并行分区）、子 Agent
权限5 门管线 + Plan 模式 + 安全路径守卫 + Bash 沙箱 + 诚实准则

2. 设计原则

来自 learn-claude-code S1-S20 教学体系 + claw0

① One loop is all you need

所有机制挂在同一个 while True 上。工具调度、权限检查、钩子触发、压缩触发——都不改循环本体。

② Hang on the loop

新功能通过钩子注入：PreToolUse、PostToolUse、Stop、UserPromptSubmit。不侵入循环代码。

③ Cheap first, expensive last

4层压缩管线：L1修剪→L2微压缩→L3预算→L4 LLM摘要。前三层免费，最后一层才调用API。

④ Files are the prompt

claw0 理念：8个文件映射8层提示词。修改SOUL.md改变人格，无需改代码。层序决定影响力。

⑤ Load when needed

两层技能加载：系统提示只放索引(~100 token/skill)，需要时通过skill_manage加载完整内容。

⑥ Errors = start of retry

三级恢复链：max_tokens升级→reactive compact→fallback model。错误不是终点，是重试的起点。

4. 模块详解

4.1 Agent 循环 — kernel/loop.py (411行)

参考: learn-claude-code s01 "One loop is all you need" + pi-mono 双层循环 + reasonix 风暴断路器

设计思路

Agent 循环是整个框架的心脏。遵循 "One loop is all you need" 原则——所有机制（工具调度、权限检查、钩子触发、压缩触发）都挂在这个循环上，不修改循环本体。采用 双层结构（pi-mono 模式）：外层处理 Agent 生命周期（follow-up 队列），内层处理单轮对话（LLM 调用→工具执行→结果收集）。

循环状态封装在 LoopState 中——包含消息历史、工具注册表、权限管线、钩子管理器、提供者等。这种设计使得状态可序列化、可恢复、可分支。

核心接口

async def agent_loop(state: LoopState) -> AsyncGenerator[AgentEvent, None]:
    """双层事件驱动 Agent 循环，yields AgentEvent 在每个生命周期阶段。"""

LoopState 关键字段: messages(对话历史), tools(ToolRegistry), provider(LLM), permissions(管线), hooks(钩子), config(LoopConfig), abort(取消信号), _follow_up/_steering(消息队列)。

内层循环 — 单轮对话

# 每轮的标准流程 1. yield TurnStarted 2. drain_steering() → 注入中轮引导消息 3. provider.create_message() → LLM 调用 + usage 追踪 4. yield LLMResponse(text, tool_blocks) 5. 构建 assistant 消息，追加到 state.messages 6. if tool_blocks: partition(tool_blocks) → 并行/串行批次 for batch: execute → yield ToolResult 追加 tool_results 到 state.messages else: 检查 follow_up 队列 → 注入或完成 7. yield TurnDone

外层循环 — follow-up 队列

Follow-up 队列是 Agent 自然停止后才处理的消息（pi-mono 模式）。例如：用户说"帮我分析工作区"→Agent 完成→系统注入 "顺便也分析一下实体结构"→Agent 继续。这不同于 steering 队列——steering 是中轮立即干预（如用户按了"停止"按钮）。

工具并行分区

ToolRegistry.partition() 将 LLM 返回的 tool_blocks 分为批次：连续只读工具（read_file, grep, glob）→并行执行（asyncio.gather，上限 8），写工具（write_file, edit_file, bash）→独占串行。这来自 reasonix 的设计——只读工具无副作用，安全并行。

风暴断路器 (Storm Breaker)

来自 reasonix agent.go。当同一工具+同一错误模式连续出现 ≥3 次时，不再简单返回错误——而是在输出中注入提示："This error pattern has repeated 3+ times. Consider changing approach." 防止 Agent 陷入死循环。

def record_error(tool_name, error_msg) -> bool:
    key = f"{tool_name}:{fingerprint(error_msg)}"
    count = error_history[key] = error_history.get(key, 0) + 1
    return count >= max_storm_repeats  # 默认 3

子 Agent 执行

run_sub_agent() 创建隔离的 LoopState（独立的消息历史、过滤的工具集、有限的轮次），在子会话中执行。用于 task 工具的后台执行——子 Agent 的结果不影响父 Agent 的消息历史，避免上下文污染。

最终就绪检查 (Final Readiness)

来自 reasonix。在 Agent 宣布完成前验证：最后一条消息是否包含工具错误（如有则提示重试或换方法）。防止 Agent 在工具失败后错误地返回"完成"。

4.2 工具系统 — kernel/tool.py (207行)

参考: reasonix tool.go Tool 接口 + pi-mono tool lifecycle hooks

设计思路

工具是 Agent 的手。设计核心是 最小接口 + 最大灵活性——Tool 是一个抽象基类，子类只需实现 execute()，可选覆盖 validate()、check_permissions()、preview()。这与 reasonix 的 Tool 接口一致——Go 的 Tool { Name(); Description(); Schema(); Execute(); ReadOnly() } 直接映射到 Python ABC。

Tool ABC 接口

class Tool(ABC):
    name: str          # 工具名称 (LLM 通过此名调用)
    description: str    # LLM 理解工具用途的描述
    parameters: dict    # JSON Schema — 自动转为 API 格式
    read_only: bool     # True = 并行安全, Plan模式可过

    async def execute(self, args, ctx) -> str: ...       # 必须实现
    async def validate(self, args) -> ValidationResult: ... # 参数校验
    async def check_permissions(self, args, ctx) -> PermissionResult: ...
    def preview(self, args) -> str | None: ...           # diff 预览

生命周期钩子

来自 pi-mono: 每个工具执行经过 prepare → validate → before_hook → execute → after_hook → finalize。before_hook 可以阻止执行（返回 block=True），after_hook 可以追加输出。钩子按注册顺序链式执行——第一个阻止结果短路后续钩子。

只读并行分区算法

# partition() 算法 — reasonix 模式 输入: [{read, id:1}, {read, id:2}, {write, id:3}, {read, id:4}] 输出: [[{read,1}, {read,2}], [{write,3}], [{read,4}]] 规则: - 连续只读工具 → 同一批次，asyncio.gather 并行 - 写工具 → 独占批次，串行执行 - concurrency_safe=False → 独占批次

工具注册

ToolRegistry.register(tool) 按名称注册。list_definitions() 生成 Anthropic API 格式的工具定义列表。remove_by_prefix("mcp__server__") 支持批量移除（reasonix 的 MCP 命名空间模式）。

4.3 权限管线 — kernel/permission.py (274行)

参考: cc permissions.ts 5步评估链 + reasonix permission.go 三态决策

设计思路

权限系统的核心问题是 在安全性和可用性之间取得平衡——太严格则 Agent 无法工作，太宽松则可能造成破坏。BLM 采用 5 门管线：从最严格的内置拒绝列表开始，逐层放宽，最后以永不旁路的安全路径守卫结束。每层可以独立配置和扩展。

5 门管线详解

Gate 0: Plan Mode 阻止所有非只读工具。用于"只看不做"的安全审查模式。 检查: if plan_mode and not is_read_only → DENY Gate 1: 内置 Deny List 硬编码的危险模式——sudo, rm -rf /, mkfs, dd, fork bomb等。 这些模式在任何情况下都不允许。不依赖用户配置。 Gate 2: Tool Check 工具自身的 check_permissions() 方法。bash 工具在此层检查 子命令和路径。可扩展——新工具覆盖此方法即可。 Gate 3: Policy 规则评估 用户配置的规则（JSON文件）。优先级: deny > allow > ask。 支持通配符(mcp__*)、内容glob(bash(rm -rf*))。 运行时可通过 PermissionPolicy 动态修改。 Gate 4: Safety Guard (永不旁路) 安全路径守卫——.git/ .env .ssh/ .bashrc 等。 即使在 bypass 模式下也必须询问。这是最后防线。

权限模式

模式行为适用场景
DEFAULT每步询问(Gate 3→ASK)CLI 交互
PLAN只读(Gate 0 阻止写)安全审查
ACCEPT_EDITS自动接受文件修改信任的文件操作
BYPASS跳过(Gate 3→ALLOW)自动化(需谨慎)
HEADLESS无人值守自动允许API/后台任务

策略规则 JSON 格式

{"deny": [{"tool":"bash","content":"rm -rf*"}],
 "allow": [{"tool":"bash(ls *)"}, {"tool":"read_workspace"}],
 "ask": [{"tool":"mcp__*"}]}

通过 load_rules_from_file() 加载，运行时可通过 switch_mode() 切换模式。

4.4 上下文压缩 — context/ (8 files)

参考: cc compact.ts 4层流水线 + hermes context_compressor.py + reasonix 三比率触发

设计思路

LLM 的上下文窗口有限（如 128K tokens）。当对话积累超过窗口时，必须压缩旧内容。核心原则是 "Cheap first, expensive last"——前三层压缩不调用 API（免费），第四层才调用 LLM 做结构化摘要（昂贵）。四层依次尝试，前一层失败或不足时才进入下一层。

三比率触发机制

来自 reasonix compact.go——不是简单的"到了 80% 就压缩"，而是三级预警：

比率阈值行为
soft_ratio50%仅通知"上下文增长中"，不触发压缩
compact_ratio80%触发自动压缩（4层依次尝试）
force_ratio90%强制压缩，跳过经济性判断

L1 修剪 (snip_compact.py)

删除中间区域的过渡性短消息（"Let me check..."、"Looking at..."）。保留头部(3条)和尾部(10条)。保留所有工具调用和工具结果。零 API 调用。

L2 微压缩 (micro_compact.py)

遍历可压缩工具（read_workspace, list_workspaces, grep, glob, ls, read_file, web_fetch）的历史结果，只保留最近 3 个，旧结果替换为 sentinel 字符串 [Old tool result content cleared]。不破坏消息结构，不调用 API。

L3 预算压缩 (budget_compact.py)

检测超过 2KB 的 tool_result，将完整内容写入 .blm_ai_temp/budget/ 目录，在原消息中仅保留头部 500 字符 + 尾部 200 字符 + 文件路径引用。Agent 需要完整内容时可以读取磁盘文件。

L4 LLM 结构化摘要 (compressor.py)

唯一需要 API 调用的层。使用 CC 的 9 段模板指导模型生成结构化摘要：Goal→Key Decisions→Files→Commands→Errors→Pending Tasks→Current Work→All User Messages→Optional Next Step。摘要注入到压缩后的消息列表，用 ## Context Summary 和 --- END OF CONTEXT SUMMARY --- 标记边界。

抗抖动策略

60 秒冷却（两次压缩间隔不小于 60s）、连续失败断路器（≥3次停止尝试）、连续无效跳过（≥2次节省<10%跳过）。摘要失败时使用确定性后备——统计工具名称和消息类型，不调用 API。

4.5 系统提示词 — prompt/composer.py (180行)

参考: claw0 s06 8层文件式架构 + hermes system_prompt.py 三层分离

设计思路

核心理念来自 claw0: 文件即提示词。修改 SOUL.md 即可改变 Agent 人格，无需改代码。8 层架构使得每个关注点独立——身份、性格、工具规范、技能、记忆、项目背景、运行时上下文、通道适配——各管各的，互不干扰。层序决定影响力——越靠前对模型行为影响越强。

为什么 8 层？

claw0 的设计通过实验验证：模型对系统提示词前面的内容给予更高注意力权重。因此最重要的行为约束（身份、诚实准则）放在 L1-L2，其次是操作规范（L3-L4），最后是辅助上下文（L5-L8）。这与 hermes 的三层分离（稳定/上下文/易变）互补——hermes 侧重缓存策略，claw0 侧重注意力权重。

8 层详解

4.6 会话管理 — session/ (5 files)

参考: pi-mono jsonl-storage.ts 树形存储 + reasonix checkpoint.go 快照回退

设计思路

会话持久化的核心需求是：支持 Fork（从历史某点创建新分支）、Rewind（回退到之前的消息）、Compact（压缩旧消息为摘要）。pi-mono 的 JSONL 树形设计完美满足这些需求——每个条目有 id 和 parentId，形成有向无环图。叶子指针（leaf entry）指向当前活跃末端，改变叶子指针即可"回退"。

JSONL 树形结构

# 条目类型 (7种) session → 文件头部 (version, id, cwd) message → 对话消息 (user/assistant/tool_result) compaction → 压缩记录 (summary, firstKeptId, tokensBefore) branch_summary→ 分支摘要 (fromId, summary) custom → 自定义数据 (扩展用) leaf → 叶子指针 (targetId → 当前活跃末端) # 树形导航 get_path_to_root(): 从 leaf.targetId 沿 parentId 链回溯 get_messages(): 遍历路径,展开 compaction 为概要消息 返回可直接注入 Agent 上下文的消息列表

Checkpoint 快照

来自 reasonix checkpoint.go。每个写工具（write_file, edit_file, save_workspace）执行前，自动在 .ckpt/ 目录保存编辑前的文件副本。命名格式: t{turn}_{filename}。回退时从指定轮次的快照恢复文件。Git-free——不依赖版本控制系统。

分支操作

BranchManager.fork(session_id, at_entry) 创建新会话，复制到分叉点的所有条目。rewind(session_id, to_entry) 将叶子指针设置到指定条目——"撤销"之后的所有操作。summarize_range() 返回指定范围内的条目元数据。

FTS5 跨会话搜索

SessionSearch 使用 SQLite FTS5 索引所有会话消息。三种调用模式：Discover（全文搜索）、Scroll（围绕特定消息查看上下文）、Browse（列出最近会话）。来自 hermes session_search_tool.py 的设计。

4.7 技能系统 — skill/ (7 files)

参考: hermes-agent 自沉淀技能 + learn-claude-code s07 两层加载

设计思路

技能是 Agent 的"肌肉记忆"——完成过复杂任务后，把流程记录下来，下次遇到同类任务自动加载执行。技能 = Markdown + YAML 元数据（hermes 模式），不是代码，不是插件。Agent 通过同样的工具调用接口读写技能——创建、查看、修补、删除。

两层加载

来自 learn-claude-code s07: 索引先行，内容按需。系统提示词中只放技能名称+一句话描述（约 100 tokens/技能），避免撑满上下文。Agent 判断某技能匹配当前任务时，调用 skill_manage(action="view") 加载完整内容。这保证了即使有 100 个技能，系统提示词也只增加约 10K tokens。

模糊修补算法

当 Agent 想修补技能中的某段文本时，可能因为空格/换行差异导致精确匹配失败。模糊修补使用 difflib.SequenceMatcher 正态化空格后比较，取 ratio > 0.7 的最佳匹配。这使得修补对格式差异鲁棒。

策展生命周期

ACTIVE → STALE(30天未用) → ARCHIVE(90天,移到.archive/)。策展器（curator.py）定期运行，只处理 Agent 自创技能，不触碰捆绑/市场技能。钉住（pin）的技能跳过所有自动流转。

安全扫描

skill/guard.py 检查 12 种高危模式（curl外传、rm -rf /、eval base64 等）+ 5 种中危模式（pip install、git clone 等）。市场安装的技能必须通过安全扫描。

4.8 记忆子系统 — memory/ (5 files)

参考: hermes-agent memory_provider.py ABC + cc memory store

设计思路

记忆系统解决"Agent 跨会话记住团队约定"的问题。核心设计: MemoryProvider ABC 支持可插拔后端（内置文件 + 未来可扩展向量数据库）。内置实现用 § 段落分隔符 管理 MEMORY.md 条目，支持添加/删除/召回。

freeze-snapshot 模式

来自 hermes: 会话开始时将 MEMORY.md 内容冻结为快照（format_for_system_prompt() 返回冻结状态）。会话内通过 memory 工具的写入立即持久化到磁盘，但系统提示词中的记忆块不变——这保持了 LLM 的 前缀缓存稳定。下次会话重新加载时自动包含新内容。

威胁扫描

memory/guard.py 在写入前检查注入模式（[SYSTEM]、<|im_start|> 等）、渗出模式（curl POST、nc、ssh 等）、破坏性模式（rm -rf /、> /dev/sd 等）。匹配的内容被替换为 [BLOCKED] 占位符。

关键接口

class MemoryProvider(ABC):
    def system_prompt_block() -> str     # 静态文本，注入提示词
    def prefetch(query, session_id) -> str  # 每轮前召回
    def sync_turn(user, assistant, ...)     # 每轮后异步写入
    def get_tool_schemas() -> list[dict]    # 暴露给 Agent 的工具

4.9 错误恢复 — kernel/retry.py (200行)

参考: learn-claude-code s11 三级恢复 + cc reactive compact

设计思路

LLM API 调用有四种典型失败模式，每种需要不同的恢复策略。核心原则: "Errors aren't the end, they're the start of a retry"。通过 classify_error() 将异常分类，然后走对应的恢复路径。

错误分类 + 恢复策略

# classify_error() → 5 种分类 TRANSIENT (timeout/connection) → retry_with_backoff(指数退避+随机抖动) OVERLOADED (429/529/503) → FallbackTracker(连续3次→降级模型) MAX_TOKENS (output truncated) → escalate(8K→16K→32K→64K)+continuation prompt CONTEXT_OVERFLOW (413/4001) → reactive compact → retry FATAL (auth/403) → 不重试，直接报错 # 退避算法 (s11: 500*2^attempt + jitter) delay = min(500ms * 2^attempt, 32s) + random(0, delay*0.5)

Max Tokens 升级链

当 Agent 输出被截断时，不放弃——逐步提高 max_tokens（8K→16K→32K→64K），并发送 continuation prompt 让模型从截断处继续。最多 3 次 continuation。

Fallback Model

FallbackTracker 追踪连续 529/503 错误。当连续过载 ≥3 次时自动触发降级——切换到备用模型或移除工具（减少 prompt 大小）。成功调用后重置计数器。
