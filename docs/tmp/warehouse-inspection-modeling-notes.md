## 讨论记录 2026-07-02：按品种查库与按仓库查库的关系

用户补充：

- 按品种查库后续是一对多关系。
- 原因是一个品种可能存在于很多家仓库。
- 按品种查库存在“最高查库次数”限制，尤其第三方查库涉及交易所付费，第三方有多查库的动机。
- 实际发生的每次查库记录，仍然是“按仓库查库记录”。

当前较强假设：

一个统一的“线下查库任务”可以同时覆盖两种查库范围，通过字段区分：

- `查库范围 = 按仓库查库`：任务本身就是一次具体仓库检查，可直接进入发布、承接、上报、仓库确认、查阅等状态流转。
- `查库范围 = 按品种查库`：任务更像一个按品种设定的查库批次或额度池，它本身约束品种、检查单位、最高查库次数、剩余待查次数；每一次真实检查都派生为一条按仓库查库记录。

这个假设下，建模上不宜把“按品种查库”简单理解成按仓库查库的筛选条件。它至少多了三个责任：

- 约束责任：限制最高查库次数，避免第三方无限制生成检查记录。
- 派生责任：每次选择某家仓库实际检查时，生成一条按仓库查库记录。
- 汇总责任：按品种任务需要看到已经检查了哪些仓库、剩余还能检查几次、最终是否完成。

暂不收敛的问题：

1. 按品种查库本身要不要有独立状态？例如：未发布、待承接、执行中、已完成、已关闭。
2. 派生出来的按仓库查库记录是否复用“线下查库任务”实体，还是另建“线下查库记录/执行记录”实体？
3. “最高查库次数”限制的是生成按仓库记录的次数，还是第三方实际上报结果的次数？
4. 按品种查库是否允许同一仓库被多次检查？如果允许，次数如何计入最高查库次数？
5. 按品种查库是否需要先指定候选仓库范围，还是第三方在执行时从该品种关联仓库中选择？

补充结论：

- 按品种查库不预先指定候选仓库范围。
- 第三方执行时可在该品种相关仓库中自由选择实际查库仓库。

由此带来的建模含义：

- 按品种查库任务不需要保存“候选仓库清单”作为必填业务字段。
- 需要保存可用额度类字段，例如 `最高查库次数`、`已查库次数`、`剩余待查次数`。
- 每次第三方选择某个仓库并发起实际检查时，生成一条从属于按品种查库任务的按仓库查库记录。
- 系统需要在生成按仓库查库记录时校验剩余次数是否大于 0。

继续悬而未决的问题：

1. 同一个按品种查库任务下，同一家仓库是否允许被重复选择？
2. 如果第三方生成了按仓库查库记录但后来没有上报结果，这次是否占用查库次数？
3. 按品种查库任务什么时候算完成：剩余次数为 0、检查时间结束、人工关闭，还是三者都可以？

补充结论：

- 同一个按品种查库任务下，同一家仓库允许被重复选择。
- 不需要建立 `按品种任务 + 仓库` 唯一约束。
- 每生成一次有效的按仓库查库记录，就占用一次查库次数。

由此带来的建模含义：

- `最高查库次数` 约束的是实际执行次数，不是仓库覆盖数量。
- `已查库次数` 可以按从属的按仓库查库记录数量计算，也可以冗余保存以便列表展示和并发校验。
- 重复选择同一仓库不是异常，不应作为业务校验错误。
- 需要定义“有效的按仓库查库记录”从哪个时点开始占用额度：创建时、发布时、承接时，还是上报时。

补充结论：

- 第三方在按品种查库任务下选择仓库并生成按仓库查库记录时，就扣减剩余查库次数。
- 不需要等到上报查库结果后才扣减。

由此带来的建模含义：

- `剩余待查次数` 的扣减触发点是“生成按仓库查库记录”。
- 创建按仓库查库记录前必须校验 `剩余待查次数 > 0`。
- 记录生成后，即使尚未上报结果，也已经占用一次查库额度。
- 按仓库查库记录需要保留 `来源按品种查库任务ID`，用于回溯额度来源。

继续悬而未决的问题：

1. 如果按仓库查库记录被撤销、删除或作废，是否返还查库次数？
2. 如果生成记录后长期未上报，是否需要超时关闭或人工处理？

阶段边界结论：

- 第一阶段不考虑复杂异常补偿场景。
- 按仓库查库记录一旦生成并扣减次数，后续撤销、删除或作废不返还次数。
- 基本假设是第三方认领/生成查库任务后，后续会走完正常流程。
- 暂不建模长期未上报、超时关闭、额度返还、异常补偿等机制。

由此带来的建模含义：

- 第一阶段只需要正向状态流转，不需要复杂反向补偿流转。
- `剩余待查次数` 可按“生成即扣减”规则维护，不必设计返还任务。
- 业务规则中需要明确：查库次数占用后不返还。

补充结论：

- 按品种查库任务的 `剩余待查次数` 扣减到 0 时，任务自动完成。
- 因为扣减由用户生成按仓库查库记录触发，所以这个自动完成可以发生在用户操作链路中。
- 检查时间结束后，当前用户操作链路先不修改任务状态。
- 检查时间到期后的状态处理，后续由定时任务完成。

由此带来的建模含义：

- 按品种查库任务需要至少包含：`最高查库次数`、`已查库次数`、`剩余待查次数`、`状态`。
- 用户生成按仓库查库记录时，任务处理顺序应为：校验剩余次数 -> 生成按仓库查库记录 -> 扣减剩余次数 -> 若剩余次数为 0 则置为完成。
- 第一阶段可以只描述“时间到期由定时任务处理”，暂不展开定时任务的触发频率、失败重试和补偿逻辑。

## 后续边界问题清单

以下问题先作为讨论清单，不代表需要一次性全部决定。

### 1. 任务层级边界

当前较稳的结构是：

- 按仓库查库：具体执行任务/记录。
- 按品种查库：上层任务，约束次数并派生多条按仓库查库记录。

还需要确认：

- 按品种查库是否只存在于“第三方查库”场景，还是交易所查库也可能按品种发起？
- 按品种查库派生出的按仓库记录，是否完全复用按仓库查库的后续流程：上报、仓库确认、交易所查阅、监管函关联？

补充结论：

- 从“线下查库”流程看，按品种查库只用于第三方查库场景。
- 按品种查库与按仓库查库不再倾向使用一个统一实体加字段区分，而是拆成两个实体。

新的实体边界假设：

- `按品种查库任务`：第三方查库专用的上层任务，负责品种、检查单位、检查类型、检查时间、最高查库次数、已查库次数、剩余待查次数、状态等额度和派生约束。
- `按仓库查库记录`：实际执行的一次仓库检查，既可由交易所直接创建，也可由第三方按仓库创建，还可由第三方按品种任务派生。

这样拆分后的好处：

- 按品种查库不需要背负仓库、仓库确认、监管函等单次执行字段。
- 按仓库查库可以专注表达一次具体检查的完整闭环。
- “按品种任务 -> 多条按仓库记录”的一对多关系更清楚。
- 交易所查库不会被迫携带 `最高查库次数`、`剩余待查次数` 这类只属于第三方按品种场景的字段。

由此带来的建模变化：

- 原先候选实体“线下查库任务”应拆成 `按仓库查库记录` 和 `按品种查库任务`。
- `按仓库查库记录` 增加可选字段 `来源按品种查库任务ID`。
- `按品种查库任务` 不直接保存查库结论；结论在派生出的按仓库查库记录上形成。
- `按品种查库任务` 的完成主要由额度耗尽或后续定时任务推动。

来源边界结论：

按仓库查库记录只有两类来源：

1. 交易所直接创建按仓库查库记录。
2. 第三方从按品种查库任务下派生按仓库查库记录。

不存在的来源：

- 第三方不能脱离按品种查库任务，独立创建一条按仓库查库记录。

由此带来的建模含义：

- 按仓库查库记录可以设置 `来源类型`，建议取值：`交易所直接创建`、`按品种任务派生`。
- 当 `来源类型 = 按品种任务派生` 时，必须有 `来源按品种查库任务ID`。
- 当 `来源类型 = 交易所直接创建` 时，`来源按品种查库任务ID` 为空。
- 第三方角色创建按仓库查库记录的入口只能来自按品种查库任务详情或待执行入口。

### 2. 承接边界

现有材料里有“承接查库任务”和“查看线下查库任务承接情况”。

需要确认：

- 如果发起时指定了第三方检查单位，第三方是否仍需要点击“承接”？
- 如果发起时没有指定第三方检查单位，是不是所有第三方都可见，并由某一家承接？
- 承接后是否锁定检查单位，其他第三方不再可操作？
- 第一阶段是否只考虑“承接成功”，不考虑拒绝、抢单冲突、超时未承接？

补充结论：

- 第三方先承接按品种查库任务。
- 交易所类似发布任务，第三方收到通知后可以承接。
- 承接带有“竞争/抢单”意味：谁先承接成功，任务就归谁。
- 现实中主要由棉花场景的“中纤局”承接，不太会出现大面积争抢。

第一阶段建模倾向：

- 保留“竞争承接”的业务语义，但不建复杂抢单系统。
- 按品种查库任务发布后，对符合条件的第三方可见。
- 第一家第三方承接成功后，任务锁定到该第三方检查单位。
- 后续其他第三方再承接时，系统提示任务已被承接。
- 不展开拒绝、排队、多人同时承接仲裁、超时释放等复杂机制。

由此带来的建模含义：

- `按品种查库任务` 需要字段：`发布状态/任务状态`、`承接单位ID`、`承接单位名称`、`承接时间`。
- 可以增加 `查库任务承接记录`，记录第三方承接动作，第一阶段至少记录承接成功。
- 承接任务需要业务规则：只有未承接的已发布按品种查库任务允许承接。
- 承接成功后，第三方才可以在该按品种任务下生成按仓库查库记录。
- “查看线下查库任务承接情况”可理解为查询按品种任务的发布、承接单位和承接时间。

## 附件原型与业务规则对照

本节来自附件原型 `线下查库` 相关 HTML 和 manifest 中“线下查库”流程的业务规则说明。

### 原型观察

线下查库主流程附件包含四类页面：

- 交割部端：线下查库创建、发布、修改、删除、上报、查阅。
- 第三方端：按仓库/按品种查库列表、按品种任务下新增查库、上报查库结果。
- 仓库端：查看查库任务、确认查库结果、上传仓库确认附件。
- 任务承接页：交割部和第三方查看第三方查库任务承接情况，第三方承接任务。

原型里出现的关键字段：

- 通用：查库范围、查库主体、检查单位、检查类型、品种、检查时间、备注。
- 按仓库查库：交割仓库、检查人员、查库结论、仓库确认附件、监管函关联。
- 按品种查库：最高查库次数、剩余待查次数、查库记录列表。
- 承接：承接单位、承接时间/状态、待承接、已承接。

原型里出现的关键状态：

- 创建/发布侧：未发布、待检查、待承接。
- 执行侧：待上报、待仓库确认、待查阅、检查完成。
- 承接侧：待承接、已承接。

### 业务规则说明的稳定信息

manifest 中“线下查库”流程规则明确了以下链路：

- 新增线下查库：
  - 保存草稿后状态为“未发布”。
  - 直接发布且已指定检查单位，状态为“待检查”。
  - 未指定检查单位，状态为“待承接”。
- 发布线下查库：
  - 前置条件是任务处于“未发布”。
  - 已指定检查单位则进入“待检查”。
  - 未指定检查单位则进入“待承接”。
- 承接查库任务：
  - 前置条件是存在未被承接的第三方查库任务。
  - 承接后更新检查单位、承接状态和任务状态。
  - 输出里明确承接状态为“已承接”，任务状态为“待检查”。
- 第三方在按品种查库下新增线下查库：
  - 前置条件是查库主体为第三方、查库范围为按品种查库、登录机构与检查单位一致、待查库次数大于 0。
  - 后置条件是保存线下查库任务，任务状态为“待检查”，并更新待查库次数。
- 仓库确认：
  - 前置条件是登录仓库存在按仓库查库任务，且任务状态为“待仓库确认”。
  - 后置条件是保存仓库确认内容，任务状态更新为“检查完成”。
- 查阅查库结果：
  - 前置条件是线下查库任务处于“待查阅”。
  - 后置条件是更新仓库监管函信息，任务状态更新为“检查完成”。

### 与当前讨论结论一致的点

- 按品种查库有独立的最高查库次数和剩余待查次数。
- 按品种查库详情下展示从属查库记录，说明“一对多”关系存在。
- 第三方在按品种查库下新增的记录，实质是按仓库查库记录。
- 生成从属按仓库记录时，会更新待查库次数。
- 承接成功后才进入待检查，承接字段不应该和最终查库结果混在一起。

### 与当前讨论结论冲突或需要收敛的点

1. 原型和规则里仍保留“第三方按仓库查库任务承接”。

   这和当前讨论结论“第三方不能脱离按品种查库任务独立创建按仓库查库记录”存在冲突。可能解释有两种：

   - 旧原型保留了更宽的第三方按仓库承接能力。
   - 业务真实边界已经收窄，下一版建模应删除或弱化这条来源。

   当前倾向：按用户确认，以“无第三方独立按仓库来源”为准，原型对应能力作为需同步收敛点。

2. 第三方上报后的状态存在不一致。

   业务规则说明写的是：第三方上报查库结果后，更新线下查库任务状态为“待仓库确认”。

   交割部端原型代码中有一处逻辑是：交易所上报后进入“待仓库确认”，第三方上报后进入“待查阅”。

   当前需要讨论：第三方上报后是否也必须经过仓库确认。

   补充结论：第三方上报按仓库查库结果后，也必须经过“待仓库确认”。

   因此，原型中“第三方上报后直接进入待查阅”的逻辑应视为需要修正的旧逻辑或原型偏差。

3. 承接对象需要拆清。

   业务规则里“承接查库任务”同时覆盖按仓库和按品种；但按当前实体拆分，承接更适合只作用于 `按品种查库任务`。

   如果保留第三方按仓库承接，则 `按仓库查库记录` 也需要承接字段；如果取消，则承接字段主要归属于 `按品种查库任务`。

### 暂定建模修正

在下一版模型里，建议不要完全照搬原型的统一“线下查库任务”对象，而是拆成：

- `按品种查库任务`：负责发布、承接、额度、派生记录。
- `按仓库查库记录`：负责一次具体检查、上报、仓库确认、查阅和监管函关联。
- `查库任务承接记录`：记录第三方对按品种查库任务的承接动作。

状态也建议分开：

- 按品种查库任务状态：未发布、待承接、待检查/执行中、已完成。
- 按仓库查库记录状态：未发布、待检查、待仓库确认、待查阅、检查完成。
- 承接状态：待承接、已承接。

### 补充状态结论

按仓库查库记录上报后的统一状态链路：

- 交易所上报查库结果：`待检查 -> 待仓库确认`
- 第三方上报查库结果：`待检查 -> 待仓库确认`
- 仓库确认后：进入后续查阅或完成节点，具体是否需要查阅仍按查库主体/业务规则确认。

第一阶段明确：任何按仓库查库记录的上报结果，都不能绕过仓库确认。

### 3. 状态边界

当前表单线索里至少出现了：未发布、待检查、待仓库确认、待查阅，以及按品种查库的完成。

需要拆成两套状态看：

- 按仓库查库记录状态：更关注具体检查流转。
- 按品种查库任务状态：更关注额度和整体完成。

待确认：

- 按仓库查库是否需要状态：未发布、待承接、待检查、待仓库确认、待查阅、已完成。
- 交易所自己检查时，是否跳过“待承接”？
- 交易所检查是否也需要仓库确认？
- 仓库确认后是否一定进入“待查阅”，查阅后是否“已完成”？

### 4. 查库结果边界

上报查库结果时，需要按查库模板明细填写检查结果、附件、备注和总的查库结论。

需要确认：

- 总体查库结论是否只有“符合要求/不符合要求”？
- 线上查库结论是“暂未发现异常/可能存在异常”，线下查库结论是“符合要求/不符合要求”，二者是否需要建成两个枚举？
- 明细里的检查结果是随着模板控件类型动态变化，还是统一保存为文本/选项值？
- 附件和备注是否按每条模板明细保存，而不是只保存在任务头上？

### 5. 仓库确认边界

仓库查看线下查库里存在“确认”动作和“仓库确认附件”。

需要确认：

- 仓库确认是所有线下查库都需要，还是只针对第三方查库需要？
- 仓库确认时只上传附件，还是也可以填写确认意见？
- 仓库确认是否改变查库结论？当前倾向应是不改变，只补充确认材料。

### 6. 监管函关联边界

查阅页面里有“是否关联监管函”和“选择监管函”。

需要确认：

- 是否只有交易所查阅时才能关联监管函？
- 是否只有“不符合要求”才需要关联监管函，还是符合要求也可以不关联？
- 监管函是引用外部同步数据，不在本流程内创建；本流程只保存关联关系。

### 7. 统计边界

“查库统计”当前基本为空，需要先决定统计服务什么判断。

可选方向：

- 按任务数量统计：线上/线下、按仓库/按品种、交易所/第三方。
- 按结果统计：符合/不符合、异常率。
- 按执行统计：第三方承接数、上报数、完成率。
- 按仓库/品种统计：某仓库被查次数、某品种被查次数。

第一阶段可以先只建查询任务和统计维度，不必展开复杂指标口径。
