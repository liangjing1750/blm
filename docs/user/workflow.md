# BLM 使用工作流建议

这份建议用于团队内推广 BLM。核心目标不是把工具介绍完，而是让产品、流程编排、前端、后端在同一份业务模型上并行工作，减少"口头理解一致、落地各画各的"这种反复。

> **标签：** 交割业务建模 / 产品到研发协同 / 流程、表单、任务、实体贯通 / 建议版本：v1.0

## 1. BLM 解决什么问题

BLM 是一个业务语言建模工作台。它把业务全景、阶段、流程、角色、节点、步骤、表单、任务、实体和附件放在同一份文档中维护，方便团队从业务理解一路下钻到系统实现。

### 面向业务理解

- 用全景视图说明业务域、价值流环节和阶段的位置。
- 用流程视图说明一个办理事项如何开始、处理、分支和结束。
- 用角色视图检查谁参与了哪些流程、节点和任务。

### 面向研发落地

- 用业务组件、业务构件沉淀后端边界和任务定义。
- 用实体、表单和状态图连接前端界面、后端数据和流程编排。
- 用预览、导出、比对、合并支撑评审和多人协作。

## 2. 四类角色的分工

### 产品经理

- 定义业务域、价值流环节、阶段。
- 把阶段拆到流程，明确触发、角色、结果。
- 下钻到节点、用户步骤、表单需求。
- 主持业务走查，确认术语和边界。

### 流程编排

- 把流程结构整理成节点、分支、连线。
- 在节点下编排任务，确认前后顺序。
- 建立表单字段与实体字段的关系。
- 检查泳道图、摘要图和异常路径。

### 前端开发

- 基于流程节点和表单设计原型。
- 补充页面交互、状态展示、校验提示。
- 把原型或说明作为流程附件沉淀。
- 反馈表单字段、用户步骤和接口缺口。

### 后端开发

- 提前定义业务组件和业务构件。
- 围绕迭代范围定义任务、实体和状态。
- 把既有服务、表、接口反向沉淀为模型。
- 与流程编排确认任务输入、输出和状态变化。

## 3. 推荐工作流程

### 第 0 步 — 确定迭代范围和建模口径

先选一个可落地的业务片区，例如"入库预约到仓单注册"，不要一开始追求全量精确。

> **负责人：** 产品经理 / **参与：** 全体

### 第 1 步 — 产品自上而下搭骨架

先建全景视图，再建阶段和流程。阶段回答"业务走到哪一段"，流程回答"一个事项如何被发起、处理和办结"。

> **负责人：** 产品经理 / **产出：** 全景、阶段、流程清单

### 第 2 步 — 后端并行沉淀稳定模块

业务组件和业务构件相对稳定，可以先从已有系统、模块、服务、表结构中整理出来。

> **负责人：** 后端开发 / **产出：** 组件、构件、初版实体、初版任务

### 第 3 步 — 流程编排下钻到节点

把流程拆成节点、分支和连线。节点下再放用户步骤、任务、表单。复杂分支先保证主干清楚，再补异常路径。

> **负责人：** 流程编排 / **参与：** 产品、后端

### 第 4 步 — 前端并行做原型和界面拆解

围绕节点和表单做页面原型，确认字段、按钮、状态、错误提示和跳转逻辑。

> **负责人：** 前端开发 / **产出：** 原型、页面清单、交互问题

### 第 5 步 — 把流程、任务、表单、实体串起来

流程编排者把节点任务接到业务构件任务，把表单字段映射到实体字段，后端补齐任务输入输出。

> **负责人：** 流程编排 / **参与：** 前端、后端

### 第 6 步 — 按三条线评审

按流程走查业务是否通，按角色走查责任是否清楚，按数据走查表单、实体、状态是否能落地。

> **负责人：** 产品经理 / **产出：** 评审问题和版本保存说明

## 4. 交割业务示例

| 建模层级 | 示例 | 建议 |
|----------|------|------|
| 价值流环节 | 主体与基础资料、入库与仓单注册、在库管理与仓单流转、仓单注销与出库。 | 作为全景横轴，尽量稳定，不要频繁因为一个流程新增而改变。 |
| 业务域 | 电子仓单系统、交割智慧监管平台。 | 作为全景纵轴，用来表达系统或业务责任边界。 |
| 阶段 | 入库预约办理、仓单注册承接、移垛与盘库、仓库仓单注销与出库。 | 相同前缀或后缀尽量合并。阶段内部可以通过流程列表展开细节。 |
| 流程 | 入库预约申请、查看预约结果、撤销入库预约。 | 如果几个单角色流程存在明显前后关系，可以考虑合并成一个流程中的节点或步骤。 |
| 节点与任务 | 填写并提交预约、校验并生成待办、审批预约、写入操作记录。 | 节点表达责任转移，任务表达系统动作或服务能力。 |

> **粒度建议：** 阶段不要太碎，流程不要太长。阶段用于组织业务位置，流程用于描述一个能被发起、办理和办结的事项。节点用于表达角色之间、角色与系统之间的责任转移。

## 5. 并行协作节奏

| 时间点 | 产品经理 | 流程编排 | 前端开发 | 后端开发 |
|--------|----------|----------|----------|----------|
| 第 1 天 | 建全景、阶段、流程草稿。 | 确认主流程和异常路径表达方式。 | 熟悉流程节点和表单范围。 | 整理组件、构件、已有实体和任务。 |
| 第 2-3 天 | 补节点、用户步骤、表单需求。 | 建泳道图、摘要图、分支和连线。 | 输出原型并上传到流程附件。 | 补实体字段、状态图、任务输入输出。 |
| 第 4 天 | 主持业务走查。 | 修正任务编排和表单实体映射。 | 确认页面状态、校验和跳转。 | 确认服务边界、数据状态和接口缺口。 |
| 第 5 天 | 固化版本说明。 | 导出预览，检查流程闭环。 | 基于模型进入开发。 | 基于模型进入开发。 |

## 6. 建模规则建议

### 阶段和流程

- 阶段名优先用业务段落，例如"入库预约办理"，少用单个按钮动作。
- 流程名优先用可办理事项，例如"入库预约申请"。
- 同一阶段下流程过多时，先合并同前缀、同后缀、同责任链的流程。
- 单角色流程如果只是前后动作，优先下沉为节点或步骤。

### 任务和数据

- 任务先归属业务构件，再被节点复用。
- 实体先表达业务数据，不急着完全等同数据库表。
- 表单字段要能追溯到实体字段；没有对应实体时，要标记为界面态或临时输入。
- 状态图只建关键生命周期，不把所有按钮都建成状态。

## 7. 推广时的验收口径

- 产品能用全景视图说明本迭代覆盖哪些业务位置。
- 流程编排能用泳道图说明节点、分支、任务和异常路径。
- 前端能从节点和表单得到页面原型、字段和交互清单。
- 后端能从组件、构件、任务、实体和状态图得到服务边界和数据口径。
- 团队能用预览或导出材料完成一次业务评审，并用保存说明记录本次变更目的。

> **落地提醒：** 第一次推广不要追求一次建完。建议先选择一个完整但不太大的流程，例如"入库预约申请"，用它跑通从全景、流程、任务、表单、实体、预览到评审的闭环，再复制方法到其它流程。
