# 业务模型设计

## 1. 结论

BLM 的核心模型收敛为 6 级：

> 价值流、业务域、阶段、流程、流程节点、步骤 + 表单/任务 + 实体。

这 6 级里，有两条主线：

- 业务流程分析：从价值流出发，逐层拆到流程节点和用户步骤。
- 业务组件设计：从任务、实体、表单片段和规则中沉淀稳定组件。

两条线不是上下级关系。流程描述业务如何发生，组件描述哪些东西可以沉淀和复用。

## 2. 六级模型

| 层级 | 回答的问题 | 典型对象 | 是否适合作为目录层级 |
| --- | --- | --- | --- |
| 价值流 | 业务靠哪些大环节推进？ | 主体资料、入库注册、在库流转、示例结算、注销出库、监管统计 | 是 |
| 业务域 | 责任边界在哪里？ | 示例仓单系统、示例平台 | 更适合作为筛选条件 |
| 阶段 | 某个价值流下有哪些业务活动段？ | 入库预约、入库办理、仓单注册、仓单注销、查库整改 | 是 |
| 流程 | 一个业务事项如何发起、办理、办结？ | 入库预约申请、现货货转审核、出库办理 | 是 |
| 流程节点 | 一个角色在责任边界内连续做什么？ | 客户提交、仓库审核、机构确认、系统同步 | 是，但在流程详情中展开 |
| 步骤 + 表单/任务 + 实体 | 节点内部如何操作、交互、校验和落数？ | 表单字段、系统任务、实体状态、规则 | 不适合直接作为流程目录 |

业务域是正式层级，但在界面上不建议放进目录树。它更适合做顶部筛选，因为业务域数量少、边界强、变化少。筛选项应以全景视图的纵轴为准，避免再维护一套和全景不一致的业务域列表。

## 3. 业务流程分析主线

业务流程分析回答：

> 业务事情从哪里开始，经过哪些阶段，形成哪些流程，谁在每个节点负责。

建议结构：

```text
业务域筛选
  示例仓单系统 / 示例平台 / 全部

业务流程视角
  价值流
    阶段
      流程
        流程节点
```

流程视角的关键原则：

- 阶段从价值流拆出来，应尽量覆盖所有流程。
- 阶段对流程要做到不重叠、不遗漏。
- 一个流程原则上只属于一个主阶段。
- 如果一个“流程”看起来横跨多个阶段，通常说明它不是流程，而是业务链路、模块或组件集合。
- 流程复用不应放在阶段层解决，复用通常发生在节点、任务、表单片段、实体和领域服务层。

例如：

```text
入库与仓单注册
  入库预约
    入库预约申请
    入库预约审核
    入库预约撤销
  入库办理
    入库办理
    终止入库
  仓库仓单注册
    仓库仓单注册申请
    仓库仓单注册结果接收
```

这里的 `仓库仓单注册` 是阶段，`仓库仓单注册申请` 或 `仓库仓单注册结果接收` 才是流程。

## 4. 业务组件设计主线

业务组件设计回答：

> 这些流程背后，哪些实体、任务、表单片段和规则可以稳定沉淀。

建议结构：

```text
业务组件视角
  业务组件
    实体
    任务
    表单片段
    规则
    关联流程
```

业务组件不是流程的上级。它是流程背后的资产承载方。

例如：

```text
仓储仓单管理
  实体
    现货仓单
    期货仓单
    期现关联
    仓单关系

  任务
    查询仓储仓单
    计算可注册数量
    确认期现关联
    生成仓单链
    校验可出库数量

  表单片段
    仓单基础信息
    货物信息
    仓房垛位信息
    审核意见
    操作记录

  关联流程
    入库办理
    仓库仓单注册结果接收
    现货货转申请
    仓单注销结果接收
    出库办理
```

这里的“关联流程”只是反向索引，不表示这些流程归属于组件。

## 5. 流程、节点、任务的边界

流程不是最小单元。流程只是可办理事项的模板。

真正可复用的内容通常在更低层：

| 对象 | 是否适合复用 | 说明 |
| --- | --- | --- |
| 流程 | 一般不复用 | 流程有明确阶段、触发、状态和办结结果 |
| 流程节点 | 可以复用一部分 | 同一角色责任动作可能跨流程出现，但仍要看上下文 |
| 系统任务 | 非常适合复用 | 查询、校验、计算、同步、状态变更 |
| 表单片段 | 非常适合复用 | 客户信息、仓库信息、仓单信息、审核意见 |
| 实体 | 必须复用 | 业务事实、状态和关系应统一 |
| 规则 | 必须复用 | 业务口径不能在多个流程里各写一套 |

因此，工具中不要建立“一个流程 = 一个组件”的关系。

更合理的关系是：

```text
流程 -> 编排节点
节点 -> 使用任务
节点 -> 绑定表单
表单 -> 引用表单片段
表单字段 -> 映射实体字段
任务 -> 读取或变更实体
组件 -> 沉淀实体、任务、表单片段和规则
```

工具交互上，业务组件视角先作为“资产目录”。当前工具已经能把流程节点中的编排任务抽成任务，把表单中的分组抽成表单片段，并在左侧目录里点击进入来源节点。后续再补“从资产目录引用已有任务、插入已有表单片段”的设计能力。

当前左侧目录先做收敛：业务组件下只展示实体、任务和关联流程。任务来自流程节点编排任务，并全部展示；关联流程由任务来源反推。表单片段和规则仍保留在模型中，但不放在目录区，避免这一层变成过重的资产清单。

## 6. 表单复用

表单可以复用，但复用的重点不是整张表单，而是表单片段、字段定义、校验规则和展示规则。

整张表单通常挂在流程节点上，有上下文、权限、状态和提交动作，不宜直接复用。

适合复用的表单片段包括：

- 客户信息
- 仓库信息
- 品种信息
- 仓单基础信息
- 货物信息
- 车船信息
- 附件上传
- 审核意见
- 操作记录

建议关系：

```text
流程节点绑定表单
表单引用表单片段
表单字段映射实体字段
表单片段沉淀在业务组件中
```

因此后续表单设计器应优先支持两类复用：一是从实体字段生成表单字段，二是从表单片段插入一组字段和校验。整表复用可以保留为“复制模板”，但不应作为主要建模关系。

## 7. 左侧目录建议

左侧目录不应再承担所有模型层级。它应该是两类导航：

```text
业务域：全部 / 示例仓单系统 / 示例平台

[业务流程] [业务组件]
```

### 7.1 业务流程视角

用于看业务推进顺序：

```text
业务流程
  价值流
    阶段
      流程
        流程节点
```

这个视角适合业务分析、流程完整性检查和低代码流程设计。

### 7.2 业务组件视角

用于看组件沉淀和资产复用：

```text
业务组件
  实体
  任务
  关联流程
```

这个视角适合产品模块设计、服务边界设计、权限菜单设计和后续应用架构分析。

实体和任务不是流程目录里的文字说明，而是资产项。实体由业务组件覆盖，任务对应节点内的编排任务。用户从组件目录点击它们时，应能回到具体数据对象、流程节点和编辑位置；关联流程则由任务来源流程反推。

左侧目录不再单独保留“实体”树。实体已经由业务组件承接，原来的“主题域”更适合收敛为“实体组”或“实体标签”：它不是新的业务层级，主要用于实体关系图分组、着色、局部聚焦，以及在组件内实体很多时做二级视觉归类。

## 8. 示例仓单系统与示例平台的建模深度

两个业务域的深度不一样。

| 业务域 | 建模深度 | 原因 |
| --- | --- | --- |
| 示例仓单系统 | 到流程级 | 主要用于说明场内系统职责边界，不设计节点和低代码编排 |
| 示例平台 | 到流程节点、表单、任务、实体 | 目标平台要支撑低代码流程、待办、留痕和监管闭环 |

这个差异很重要。不能为了模型整齐，强行给示例仓单系统拆节点。

## 9. 建模顺序

推荐顺序：

1. 先定价值流。
2. 再定业务域边界。
3. 在每个业务域下，按价值流拆阶段。
4. 在阶段下列流程，要求流程不重叠、不遗漏。
5. 对目标平台的流程继续拆流程节点。
6. 对流程节点补用户步骤、表单、系统任务。
7. 把表单字段映射到实体字段。
8. 从任务、实体、表单片段和规则中沉淀业务组件。
9. 回头检查组件和流程的关系，不把组件误当成流程上级。

## 10. 一句话

阶段组织流程，流程编排节点，节点使用组件资产。组件沉淀实体、任务、表单片段和规则。
