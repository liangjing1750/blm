# 业务建模思考

我的理解是：业务建模是反复校正认知，螺旋式前进的过程：

- 自上而下：先沿业务时间线和价值流梳理全景，知道业务大体怎么发生、怎么创造价值。
- 自下而上：再从“流程、数据、规则”里补充细节，反过来修正前面对业务的理解。

BLM工具，吸收了《聚合架构》这本书的以下观点：
- 数据长在流程上，业务架构包含数据架构。
- 以一个角色连续的动作序列划分流程节点。
- DDD更偏向于技术人员的领域建模，业务人员更需要流程和数据的视角。

## 1. 业务按照时间线/流程梳理

建模刚开始时，不建议先陷入数据库、字段、页面和系统功能。

更自然的思考过程是不断的反问：

> 在这个时间点，什么角色，干了什么。

这句话有两个作用。第一，它帮助团队先梳理业务时间线。第二，它把角色、动作、结果先拉到台面上，避免一开始就进入系统实现细节。

以示例监管业务为例，最开始看到的往往是一条粗时间线：

`货物入库 -> 货物在库 -> 货物出库`

继续往下看，入库不是一步完成的。它可能拆成入库预约、审核回复、办理入库、生成或归档仓单。

- 再往前追，想要预约，必须先是平台用户，于是前面又会补出“用户管理”。
- 再往下拆，办理入库会继续拆成不同角色连续动作形成的流程节点。
- 再往旁边看，入库材料可能需要视频截图、视频回放，于是又会识别出“视频监控”这样的支撑能力。

这个例子说明，业务不是一条线就能解释完。

时间线能帮我们看先后顺序，能力边界能帮我们看哪些事情应该归到同一块，建模时要允许自己来回修正。

比如：一开始看起来像一个流程，细化以后可能发现它跨了两个角色职责，需要拆成两个节点。

## 2. 流程的六级模型定义

现在更准确的说法是六级模型：

> 价值流 -> 业务域 -> 阶段 -> 流程 -> 流程节点 -> 步骤/表单/实体/任务

这里把 `业务域` 明确放进第 2 级，不是为了多造一个层级，而是因为企业架构里经常需要同时回答两个问题：

- 横向看：企业有哪些价值流，业务活动放在哪个大环节里。
- 纵向看：不同产品、业务线、监管对象或系统边界在同一价值流下有什么相同和差异。

这也是为什么全景视图适合做成二维矩阵，而不是一棵目录树。横轴放价值流，纵轴放业务域，单元格里再放阶段和流程。PPT 第 3 页表达的就是这个意思：先把整盘业务活动放到一张图里，再看每个业务域在不同价值流下承担什么职责。

![价值流与业务域全景矩阵](screenshots/16_six_level_panorama_matrix.png)

```text
                 价值流 A        价值流 B        价值流 C
业务域 1        阶段/流程        阶段/流程        阶段/流程
业务域 2        阶段/流程        阶段/流程        阶段/流程
业务域 3        阶段/流程        阶段/流程        阶段/流程
```

从某个单元格继续往下钻，就是 PPT 第 4 页那类阶段详情图：先选中一个阶段，再看这个阶段里有哪些流程，以及这些流程之间大致如何衔接。

![阶段详情下钻视图](screenshots/17_six_level_stage_detail.png)

```text
价值流
  业务域
    阶段
      流程 A -> 流程 B -> 流程 C
        流程节点
          步骤 / 表单 / 实体 / 任务
```

| 层级 | 主要回答的问题 | 在 BLM 里的表达 |
| --- | --- | --- |
| 价值流 | 企业靠哪些大环节创造价值？ | 全景视图横轴，通常 5-7 个，尽量覆盖全域 |
| 业务域 | 哪些产品、业务线或责任边界需要分开比较？ | 全景视图纵轴，也可作为筛选条件 |
| 阶段 | 某个价值流下有哪些稳定业务活动段？ | 阶段卡片，可容纳多个流程 |
| 流程 | 一个业务事项如何被发起、办理、办结？ | 可实例化的流程模板 |
| 流程节点 | 某个角色在责任边界内连续做什么？ | 流程图中的节点，表达责任转移 |
| 步骤/表单/实体/任务 | 节点内部如何操作、交互、落数和执行？ | 用户步骤、表单片段、实体字段、编排任务和规则 |

价值流适合放在业务全景图的横轴上。它不追求执行顺序里的每个细节，也不直接落到工作流引擎。它更像企业架构里的业务地图，用来说明价值如何从前到后流动。价值流太少，看不出业务差异；太多，又会退化成流程清单。

业务域适合放在全景图的纵轴上。它不是旧式“子域”概念，也不一定对应系统模块。它更像一个观察业务差异的切面：同样是图书馆借阅，分馆、线上借阅、馆际互借可能共享一批读者、书目、馆藏、借阅记录，但规则、角色和办理节点会不同。

阶段更像价值流下的稳定业务能力包，也常常带有生命周期含义。比如 `仓库管理`、`品种参数管理`、`仓单注册`、`仓单注销`、`风险监管`，都可以作为阶段或阶段卡片。阶段可以表达先后，也可以表达分流，但这里的分流只是业务关系，不需要引入 BPMN 网关那样复杂的控制逻辑。

流程是可实例化的办理模板。它围绕一个主要业务对象，由触发事件启动，经过角色、系统或规则节点，使业务对象从一个状态进入另一个状态。流程才更接近低代码平台、Flowable 或 BPMN 模板。

流程节点是一个角色在一个责任边界内的连续动作。这个标准比较好用：换角色、换目标、等待他人、进入审批、切到系统自动处理、产生关键状态变化，通常都意味着节点边界出现了。

第六级不是一个单一对象，而是节点内部的落地内容。这里可以拆成四类：用户操作步骤、表单/片段、实体/字段、系统编排任务。用户步骤面向产品和业务人员，描述查看、填写、选择、上传、确认、提交；编排任务面向研发和低代码实施，描述查询、校验、计算、服务调用、状态变更、通知、补偿；表单和实体负责把用户输入、业务对象和数据落点连起来。

## 3. 价值流和业务域

企业架构的一个重要目的，是把企业里的业务活动看作一盘棋，而不是只看某个系统、某张表、某个流程或某个页面。

BLM 里的二维全景表格，就是为了先回答：

> 这件业务活动在整盘棋里的位置在哪里？

价值流提供的是全局感。它不追求把每个流程的细节都讲完，而是尽量把企业里所有重要业务活动都囊括进来，让团队知道业务从哪里产生、经过哪些大环节、最后如何形成结果。价值流如果只覆盖主线，很多支撑工作、治理工作、风险控制工作就会被漏掉；如果拆得太碎，又会退化成流程清单。

业务域提供的是对比视角。它不是简单地把系统分成几块，而是把多个产品、多个业务线、多个监管对象分开来看，比较它们的相同点和差异点。

例如，同样是仓单业务，不同品种、不同机构、不同市场可能有不同规则。但这些业务也会共享用户、权限、机构、仓库、品种、视频、消息、附件、审核等通用能力。业务域的价值就在这里：

- 对新业务，可以在通用组件基础上快速搭建，避免每次从零开始。
- 对旧业务，可以把分散实现拉回同一套治理口径，减少重复建设。
- 对差异化能力，可以清楚说明“这里为什么不同”，而不是混在一堆页面和接口里。

所以价值流和业务域的关注点不同。

价值流强调“全局覆盖”：企业有哪些业务活动，放在什么位置。业务域强调“横向对比”：多个产品或业务线之间哪些相同、哪些不同，哪些能力可以复用，哪些规则必须保留差异。

把业务活动结构化为业务组件，目的不是为了多造一个概念，而是为了提高复用和管理规范。业务组件让团队能把一组稳定能力沉淀下来，后续流程、任务、实体、规则都可以回到组件里归档和治理。

## 4. 阶段和流程的区别

阶段回答的是：

> 业务走到哪一段了？这一段用来组织哪些相关流程？

流程回答的是：

> 为了得到一个明确业务结果，业务通常怎么被发起、处理和办结？

阶段更像业务全景里的业务段落。它帮助团队把一个大的业务过程切成几段，让大家先看到业务从哪里开始，经过哪些关键位置，最后走到哪里。阶段可以承载多个流程，也可以表达这些流程之间的先后、并列或衔接关系。

流程则更接近可实例化的办理模板。一个流程通常有触发事件、发起角色、主要业务对象、节点流转、输入输出和结束结果。比如“入库预约”可以是一个流程，因为它能被发起，有填写材料、校验规则、提交结果和状态变化。

判断一个概念是阶段还是流程，我会用一个简单标准：

> 能不能产生流程实例？能，就是流程。只是用来归类多个流程、组织业务视图、表达一段业务位置，大概率是阶段。

`仓单注册` 这个词就很典型。它既可以是阶段，也可以是流程名，取决于颗粒度。如果下面还有 `仓库仓单注册`、`厂库仓单注册`、`免检品牌仓单注册`，那 `仓单注册` 更适合作为阶段；下面这些能被发起和办结的事项，才是流程。

判断一个概念是不是流程，可以看几件事：

- 有没有触发事件或发起人。
- 有没有主要业务对象，比如仓单、仓库、品种、合约、示例预报。
- 有没有开始状态和结束状态。
- 有没有角色到角色、角色到系统、系统到角色的责任转移。
- 有没有待办、审批、记录、留痕或办结结果。
- 未来能不能变成低代码流程模板。

阶段里可以对流程做分组，用来让同一阶段下的流程更好浏览和维护。但流程组不建议作为显式的业务架构层级。讨论业务位置时看阶段，讨论可办理事项时看流程，只是流程数量多了以后，才在阶段内部做轻量分组。

## 5. 业务组件是什么？

业务组件回答的是：

> 这组稳定能力应该沉淀在哪里，未来由谁复用和治理？

它比流程更稳定，也比单个任务更完整。流程描述一件事情怎么办，业务组件描述一类能力怎么被沉淀、复用和管理。

例如，一个“仓库管理”组件里，可能包含仓库基础信息、仓库启停用、仓库资质、仓库容量、仓库权限、仓库查询服务等能力。不同流程都可能使用它：入库预约要选择仓库，仓单注册要校验仓库资质，风险监管要查看仓库库存和视频。

业务组件适合承载这些内容：

- 可复用的任务定义，比如查询仓库、校验仓库状态、保存仓库信息。
- 稳定实体，比如仓库、仓单、品种、机构。
- 通用规则，比如仓库启用状态、品种准入、权限边界。
- 服务或系统动作，比如查询、校验、计算、写入、通知。

业务组件不是阶段的下级，也不是流程的下级。它是能力归属。一个组件里的能力可以被多个阶段、多个流程、多个业务域复用。

这也是为什么 BLM 里要把“流程怎么走”和“能力归哪里”分开。阶段帮助看业务顺序，流程帮助看办理过程，业务组件帮助看能力复用和治理边界。三者互相引用，但不要互相替代。

## 6. 表单、实体的区别

表单不是实体。这个边界很重要。

实体回答的是：

> 业务世界里有哪些稳定对象，它们有什么状态、规则和生命周期？

表单回答的是：

> 某个场景下，用户需要看什么、填什么、确认什么？

比如 `仓库` 是实体，但可能有多个表单使用它：仓库新增表单、仓库变更表单、仓库查询表单、仓库启停用表单、仓单注册时的仓库选择区。同一个实体字段，在不同表单里的表现也不同。有时必填，有时只读，有时隐藏，有时是查询条件，有时是审批展示字段。

我觉得更稳的关系是：

- 实体字段沉淀标准事实，例如 `warehouse.name`、`warehouse.capacity`。
- 表单字段表达当前场景，例如“仓库名称”，可以绑定到实体字段。
- 表单挂在流程节点上，说明这个节点里谁看、谁填、谁确认。
- 节点决定当前角色、当前上下文和提交后的业务结果。
- 编排任务负责提交后的查询、校验、写入、通知和流转。

一个表单可能写多个实体，一个实体也可能被多个表单维护。所以不要从表单直接倒推出实体，更不要把数据库表简单等同于页面表单。

这也影响产品和研发的分工。

产品经理不只是画页面，而是要把“业务人员如何办事”说清楚，包括用户步骤、表单定义、字段含义、校验口径、办理路径和异常场景。研发也不只是建表，而是要把“系统如何保证这件事成立”说清楚，包括实体、聚合、状态机、接口、事务一致性、权限、审计、幂等和补偿。

中间最好有一个架构或 BA 的翻译层。它负责把用户步骤抽成流程节点，把表单字段映射到实体字段，把状态变化沉淀到实体生命周期里，把流程规则和领域规则分开放。否则低代码平台很容易把领域模型拖成一堆页面字段。

一句话说，产品经理定义“业务人员如何办事”，研发定义“系统如何保证这件事可靠成立”，架构师负责让流程、表单、实体三套模型对齐。

## 7. 使用BLM工具

BLM工具里，不试图用一张图解决所有问题，而是保留几种互相引用的模型。

- 全景视图承载价值流、业务域和阶段，让团队先看到业务地图。
- 业务组件帮助团队看清能力复用和治理边界。
- 流程模型承载可实例化的办理事项，后续可以靠近 Flowable 或低代码流程模板。
- 节点模型承载角色职责，是业务人员和研发人员对话的最小责任单元。
- 表单模型挂在节点下，表达产品和业务视角的输入输出。
- 编排任务挂在节点下，表达研发和低代码实施视角的系统动作。
- 实体模型独立维护，再被表单、节点和编排任务引用。

这样做的好处是，模型之间有关联，但不会互相吞掉。流程图不是页面原型，表单模型不是领域模型，实体模型也不能替代业务人员对办理过程的理解。

团队使用时不用把所有概念都做全，可以先用简单结构降低使用成本，随着模型复杂度上升，再逐步增强阶段引用、跨阶段复用、全景视图和流程详情图。
让团队在建模时能不断把认知沉淀下来，并且能在后续讨论中继续修正。

实际建模时，可以按这个顺序推进：

1. 先写出业务的一条粗时间线或价值流。
2. 明确业务域，比较不同产品或业务线的相同点和差异点。
3. 把价值流切成几个业务阶段。
4. 找出每个阶段里最关键、可实例化的业务流程。
5. 回头整理业务组件，确认流程、任务、实体和规则归属于哪些能力边界。
6. 对重点流程继续拆节点，明确角色职责。
7. 对节点继续拆用户步骤、表单、编排任务、数据、状态和规则。
8. 把表单字段映射到实体字段，把流程状态变化映射到实体生命周期。
9. 最后再回头校正价值流、业务域、阶段、流程和业务组件颗粒度。

这套顺序不是硬性流程，只是一个帮助团队开始讨论的抓手。

真正重要的是：每一轮建模之后，团队都应该比上一轮更清楚业务位置、业务差异、能力边界、业务顺序、角色职责、表单语义、实体事实和规则落点。
