# BLM 五步法开发规范

## 1. 核心原则

开发 BLM 功能时，目标不是快速补一个界面，而是把旧版能力、业务语义、Angular 架构和可验证行为统一起来。

五步顺序固定：

```text
需求梳理
-> 概要设计
-> 详细设计
-> 实现代码
-> 设计并实现用例
```

除非用户明确要求直接修一个小 bug，否则不要跳步写代码。涉及旧版功能复刻、工作台重构、协作同步、数据模型、复杂 UX 时，必须按五步走。

文档不是事后总结，而是设计状态的载体。中大型任务应写入或更新：

- `specs/<编号-主题>/requirements.md`
- `specs/<编号-主题>/design.md`
- `specs/<编号-主题>/tasks.md`
- `specs/<编号-主题>/status.md`

小任务至少在最终回复中说明：需求判断、设计取舍、验证结果、剩余风险。

## 2. 信息来源优先级

BLM 开发必须先吸收项目长期约束，再看旧版代码和截图。

固定读取顺序：

1. `AGENTS.md`

   - 重点理解：业务阶段、业务子域、流程资产、构件、文档可审计。

3. `docs/steering/architecture.md`
   - 本地优先、文件驱动、文档格式可读可迁移、数据模型边界。
   - 重点理解：不要为了当前 UI 便利破坏业务概念边界。

4. `docs/steering/quality.md`
   - 兼容打开、保存、预览、导出；复杂交互需要用户旅程回归。

5. `docs/angular-lost-feature-recovery.md`
   - 已恢复能力、未恢复能力、哪些不是“丢失”而是尚未迁移。

6. 当前 Angular 模块代码：
   - `frontend-angular/src/app/shell/`
   - `frontend-angular/src/app/core/`
   - `frontend-angular/src/app/shared/`
   - `frontend-angular/src/app/workbenches/`

7. 旧版参考代码：
   - `C:\Users\Administrator\Desktop\project\blm_old`
   - 只作为只读参考。
   - 不允许把旧版 JS 复制回 Angular 源码。

8. 视觉等价迁移技能：
   - `C:\Users\Administrator\.codex\skills\visual-equivalence-migration\SKILL.md`

如果没有体现这些来源的吸收结果，不要直接进入实现。

## 3. 第一步：需求梳理

需求梳理要回答：

```text
这个功能属于哪个工作台？
它是旧版能力复刻、Angular 丢失能力恢复，还是新能力？
旧版是否已有？如果有，旧版真实运行路径在哪里？
是否涉及数据模型？如果涉及，是否必须先请用户确认？
输入是什么？
输出是什么？
用户看到的界面状态有哪些？
只读态、编辑态、等待态、空态、错误态分别是什么？
是否涉及协作同步、远端修改、本地未提交、版本号？
是否涉及双窗口并发？
本轮不负责什么？
验收旅程是什么？
```

BLM 特别注意：

- 不要把“截图像不像”简化为颜色和大小。要拆成 DOM、尺寸、间距、滚动容器、层级、状态、行为。
- 不要把旧版代码当成可复制资产。旧版是行为证据，不是 Angular 架构约束。
- 不要主动改后端数据模型。
- 当前文档模型以 `uid` 为主，不要为了兼容历史假设重新引入 `id` 路径。
- 如果功能涉及团队空间、属性、版本、协作状态，必须确认保存后另一个窗口是否能看到。

## 4. 第二步：概要设计

概要设计先定义模块边界，再定义组件或类。

必须定义：

```text
模块归属：
  shell / core / shared / workbenches/<name>

主入口：
  用户从哪个按钮、tab、快捷键进入？

读模型：
  查询逻辑在哪里？
  是否需要 Query / Adapter / Service？

写模型：
  修改逻辑在哪里？
  是否会调用 ApiService / SyncService / DocumentStore？

UI 组件：
  是否已有公共组件可复用？
  是否需要新增公共组件？

状态：
  只读 / 编辑 / 加载 / 错误 / 空态 / 并发冲突如何表达？

验证：
  单元测试覆盖什么？
  浏览器旅程覆盖什么？
  是否需要旧版视觉导出对比？
```

BLM 的概要设计原则：

- 查询与修改分离。
- UI 组件不要承载核心业务规则。
- 壳层只负责入口、弹窗、工作台挂载和公共状态，不应继续膨胀业务逻辑。
- 工作台内部逻辑应留在对应 `workbenches/<name>/`。
- 真正公共的按钮、弹窗、等待态、确认框、滚动框放到 shared/core shell 层。
- 组件样式优先放组件 SCSS，不继续堆到 `styles.scss`。
- 旧版等价迁移要先规划导出对比脚本，而不是先调 CSS。

## 5. 第三步：详细设计

详细设计要落到具体文件和对象。

每个新增或改动对象说明：

```text
职责：
  它负责什么？

不负责：
  哪些逻辑不能放这里？

输入：
  接收哪些数据？

输出：
  返回什么或改变什么状态？

状态生命周期：
  初始化、用户操作、保存、同步、销毁如何流动？

失败行为：
  API 失败、校验失败、并发修改、只读文档如何处理？

验证方式：
  用什么测试或浏览器旅程证明？
```

适用于 BLM 的典型拆分：

```text
core/document
  文档模型、属性读写、规范化、纯函数。

core/sync / core/collaboration
  同步、远端修改、本地未提交、协作在线状态。

core/shell
  弹窗、等待态、历史记录、打开文档、通知、tab、sidebar 等壳层公共能力。

shared
  跨工作台复用 UI 或布局组件。

workbenches/panorama
  全景视图、角色管理、术语、字典、规则。

workbenches/process
  价值流、阶段、流程、节点、角色视图。

workbenches/component
  构件、实体关系图、状态图。

workbenches/support
  使用手册、反馈建议。
```

如果文件或类名里仍有 `Legacy*`：

- 先判断它表示旧数据结构适配，还是旧运行时代码残留。
- 数据适配命名不能机械删除。
- 要清理必须先建立新语义命名和迁移路径。

## 6. 第四步：实现代码

实现规则：

- 小步实现，保持改动集中。
- 不恢复旧版 `app/*.js`。
- 不把旧版 HTML 字符串拼接带回 Angular。
- 不新增浏览器原生 `alert/prompt/confirm`。
- 等待态用公共等待弹窗。
- 删除、清理、覆盖类操作用自定义确认框。
- 样式不要继续污染 `styles.scss`，除非是明确的 shared/global rendered content。
- 新增复杂业务逻辑、适配器、复杂 UI 交互时写三级注释：
  - 模块意图
  - 关键流程
  - 边界细节

实现前后必须检查：

```powershell
git status --short
git diff --stat
```

涉及 Angular 前端时，常规验证：

```powershell
cd C:\Users\Administrator\Desktop\project\blm\frontend-angular
npm.cmd test -- --watch=false
npm.cmd run build
```

注意：

- `npm.cmd test -- --watch=false` 是可靠命令。
- 不使用 `npm.cmd test -- --run`。
- 构建可能有既有 budget warning，exit code 为 0 即构建通过。
- 构建会更新根目录 `app/` 产物，提交前要一起检查。

## 7. 第五步：设计并实现用例

测试证明用户行为，不证明方法存在。

BLM 常用测试层次：

### 7.1 单元测试

适合：

- 文档属性读写。
- 数据规范化。
- uid 关系解析。
- 角色使用统计。
- 阶段/流程/构件关系计算。
- 协作状态判断。
- 查询与过滤。

### 7.2 组件测试

适合：

- 壳层按钮。
- 弹窗显示。
- tab 切换。
- 编辑态/只读态。
- 等待态。
- 表单输入与保存。

### 7.3 浏览器旅程测试

适合：

- 打开文档。
- 新建文档后界面刷新。
- 修改属性后另一个窗口可见。
- 立即同步等待态。
- 归档版本、历史记录、只读打开。
- 目录抽屉滚动、折叠、展开。
- 旧版视觉等价。

### 7.4 双窗口并发测试

涉及协作同步时必须考虑：

```text
A 窗口打开文档。
B 窗口打开同一文档。
A 修改并同步。
B 是否出现远端修改提示？
B 点击打开/同步/刷新后是否看到最新内容？
B 的本地未提交是否被正确保留或提示？
```

### 7.5 视觉等价验证

涉及旧版复刻时必须验证：

```text
旧版截图 / DOM / computed style / bounding box。
新版截图 / DOM / computed style / bounding box。
差异解释。
用户旅程是否一致。
```

不要只说“看起来差不多”。

## 8. 完成门槛

一个 BLM 功能切片完成，需要同时满足：

- 需求边界清楚。
- 旧版依据或新功能依据清楚。
- 没有引入旧 JS 回 Angular 源码。
- 没有未经确认修改后端数据模型。
- 查询与修改边界清楚。
- UI 状态完整：只读、编辑、等待、空态、错误态。
- 涉及协作时完成双窗口思考或验证。
- 相关测试通过。
- `npm.cmd run build` 通过。
- 剩余风险明确写出。
- 如已提交，提交信息为中文。

## 9. 常见任务套用方式

### 9.1 旧版功能复刻

```text
需求梳理：
  明确旧版入口、状态、功能范围。

概要设计：
  定义 Angular 落点和公共组件复用策略。

详细设计：
  对照旧版导出的 DOM/style/行为证据。

实现：
  Angular 模块内实现，不复制旧 JS。

用例：
  新旧截图/样式对比 + 用户旅程验证。
```

### 9.2 协作同步修复

```text
需求梳理：
  明确本地未提交、远端待同步、版本号、在线用户分别是什么。

概要设计：
  定义 SyncService / CollaborationService / ShellComponent 的边界。

详细设计：
  写清楚什么时候拉取、什么时候提交、什么时候只提示不覆盖。

实现：
  不在 tab 切换等 UI 操作中误触发协作重连。

用例：
  单窗口保存 + 双窗口并发验证。
```

### 9.3 样式清理

```text
需求梳理：
  明确是公共样式、组件样式，还是疑似废弃样式。

概要设计：
  公共样式进 shared，工作台样式回组件。

详细设计：
  对照 docs/refactor/styles-classification.md。

实现：
  小批迁移，不一次性删除大段全局样式。

用例：
  build + 关键页面浏览器截图验证。
```

### 9.4 新增工作台能力

```text
需求梳理：
  判断是否涉及数据模型，若涉及先确认。

概要设计：
  定义工作台内部 query/action/view 分层。

详细设计：
  明确状态、输入输出、保存同步链路。

实现：
  落在对应 workbenches 模块，不塞进 shell。

用例：
  组件测试 + 用户旅程测试。
```
