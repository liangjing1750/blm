# 构件工作台三级 Tab 拆分五步法设计

## 1. 需求梳理

### 1.1 功能归属

本设计属于 Angular 构件工作台：`frontend-angular/src/app/workbenches/component/`。

它不是旧版能力的逐像素复刻，而是对现有 Angular 构件工作台的信息架构重组。当前页面已经有组件、构件、任务定义、实体定义等能力，但“组件构件”tab 同时展示组件、构件、实体和任务，导致一个视图承担过多阅读目标。

### 1.2 这轮负责什么

构件工作台三级 tab 调整为四个：

1. 业务组件
2. 业务构件
3. 任务定义
4. 实体定义

“业务组件”和“业务构件”替代原来的“组件构件”。“任务定义”和“实体定义”保留为构件工作台内的独立 tab。

业务组件视图只负责总览：有哪些业务组件，每个业务组件下有哪些业务构件。

业务构件视图只负责详情：一个业务构件有哪些实体和任务，并能返回业务组件视图。它的交互参考流程工作台里的“阶段视图 -> 流程组/流程视图”层级切换：先看集合，再进入某个业务对象的细节。

### 1.3 这轮不负责什么

本轮不重做实体定义编辑器。

本轮不重做任务定义编辑器。

本轮不把应用服务放进构件工作台。应用服务属于应用工作台，构件工作台里的历史 `service/orchestration` 代码路径要视为待清理遗留，不作为新 UX 的入口。

本轮不引入新的业务数据结构。仍复用：

- `businessComponents`
- `businessConstructs`
- `entities`
- `taskDefinitions`

### 1.4 输入和输出

输入是当前文档中的业务组件、业务构件、实体和任务定义。

输出是两个更清晰的构件视图：

- 业务组件总览视图。
- 业务构件详情视图。

用户操作输出是 UI 状态变化，不改变文档模型结构：

- 当前构件 ID。
- 当前三级 tab。
- 从组件总览进入构件详情。
- 从构件详情返回组件总览。

### 1.5 用户应该关注什么

用户在业务组件视图里关注“能力边界的分组”：哪些业务组件存在、每个组件下沉淀了哪些业务构件。

用户在业务构件视图里关注“一个构件的资产”：这个构件下有哪些实体、有哪些任务定义，是否足够支撑该构件的业务能力。

### 1.6 开发者应该关注什么

开发者要把读模型和写模型分开：

- 业务组件视图只做查询和导航。
- 业务构件视图只做查询和轻量入口，不在这里重做任务/实体编辑。
- 新增的构件选择状态只放 UI 状态，不写入业务文档。

开发者还要清理命名边界：

- 构件工作台内不再把“组件构件”作为用户可见 tab 文案。
- 构件工作台内不再暴露“应用服务”三级 tab。
- 若代码里保留 `service/orchestration` 类型，必须在后续实现中确认是否删除或迁移到应用工作台，不能继续作为构件工作台 UX 的事实入口。

### 1.7 验收旅程

Given 文档里有多个业务组件，每个组件下有若干业务构件，并且构件关联了实体和任务定义。

When 用户进入构件工作台。

Then 三级 tab 显示“业务组件 / 业务构件 / 任务定义 / 实体定义”。

When 用户在业务组件视图点击某个构件。

Then 页面切换到业务构件视图，并显示该构件的实体和任务。

When 用户直接打开业务构件 tab 且没有当前构件。

Then 默认显示第一个业务构件。

When 用户在业务构件视图点击返回。

Then 页面回到业务组件视图，并保留当前构件上下文。

## 2. 概要设计

### 2.1 信息架构

构件工作台的四个三级 tab 按阅读层级排列：

1. 业务组件：组件总览，卡片式展示。
2. 业务构件：单构件详情，承接从组件卡片进入的上下文。
3. 任务定义：现有任务定义管理。
4. 实体定义：现有实体关系图和状态图。

这个顺序把“组件 -> 构件 -> 任务/实体资产”放在前两层，把已有编辑型工作台放在后面。它避免用户一进入构件工作台就看到过多细节。

### 2.2 主入口

主入口仍是构件工作台。

三级 tab 入口由 `ComponentWorkbenchComponent.activeTab` 管理。当前 `component` tab 需要拆成：

- `businessComponent`
- `businessConstruct`

建议最终类型为：

```ts
type ComponentTab = 'businessComponent' | 'businessConstruct' | 'taskDef' | 'entity';
```

历史 `service`、`orchestration` 不再属于构件工作台 tab 类型。若仍需兼容旧 UI 状态，读取时应降级到 `businessComponent`。

### 2.3 读模型

读模型全部来自当前文档：

- 业务组件：`businessComponents`
- 业务构件：`businessConstructs`
- 构件实体：实体的 `businessConstructUid` 或 `businessConstructUids`
- 构件任务：任务定义的 `constructUid`

建议把查询封装为组件内部的纯方法，后续如果继续变复杂，再提取 adapter/query：

- `constructsForComponent(component)`
- `entitiesForConstruct(construct)`
- `taskDefsForConstruct(construct)`
- `selectedConstruct()`
- `firstConstruct()`

### 2.4 写模型

本轮不新增业务写模型。

只允许已有操作继续存在：

- 新建/编辑业务组件。
- 新建/编辑业务构件。
- 任务定义编辑仍在任务定义 tab。
- 实体定义编辑仍在实体定义 tab。

业务组件视图点击构件、业务构件视图切换构件，只写 UI 状态，不修改文档。

### 2.5 UI 状态

新增或复用一个 UI 状态：

```ts
selectedConstructId: signal<string>
```

状态规则：

- 从业务组件点击构件时设置。
- 打开业务构件 tab 且为空时，回落到第一个构件。
- 删除当前构件后，回落到同组件下下一个构件，再回落到全局第一个构件。
- 返回业务组件视图时不清空，便于高亮当前构件。

是否写入 `runtime.ui` 可在实现时决定。若现有构件工作台 tab 状态已写入 `runtime.ui`，则当前构件也可写入，保持刷新后上下文稳定。

## 3. 详细 UX 设计

### 3.1 业务组件视图

业务组件视图是总览页，不展示实体和任务明细。

页面结构：

```text
Toolbar
  新建业务组件
  新建业务构件
  搜索组件/构件

Component Grid
  Component Card
    组件名称
    组件类型/说明
    构件数量
    构件列表
      构件项：名称、实体数、任务数
      点击进入业务构件视图
    卡片操作：编辑组件、添加构件
```

组件卡片不应嵌套复杂卡片。构件项可以是紧凑列表行或轻量 chip，但要能扫描数量和名称。

每个构件项展示：

- 构件名称。
- 关联实体数。
- 关联任务数。

不在该层展示实体名和任务名。原因是总览视图的阅读目标是“组件下有哪些构件”，不是“构件的全部资产”。

空状态：

- 没有业务组件：显示新建业务组件入口。
- 有业务组件但没有构件：组件卡片内显示“暂无业务构件”，并提供添加构件入口。

交互：

- 点击构件项：设置当前构件，切换到业务构件。
- 点击组件编辑：打开现有组件抽屉。
- 点击添加构件：打开现有构件抽屉，并预填所属组件。

### 3.2 业务构件视图

业务构件视图是详情页，首屏回答：“这个构件有什么资产？”

页面结构：

```text
Header
  返回业务组件
  构件选择器
  编辑构件

Construct Summary
  构件名称
  所属业务组件
  简要说明/空说明提示
  实体数、任务数

Main Content
  左列：关联实体
    实体列表
    字段数量
    进入实体定义

  右列：关联任务
    任务定义列表
    类型/目标/节点引用数
    进入任务定义
```

布局不应该把实体和任务混成一长串。建议桌面端左右两列，窄屏上下排列。

每个实体项展示：

- 实体名称。
- 字段数量。
- 可选的状态字段数量。

每个任务项展示：

- 任务名称。
- 任务类型。
- `target/address` 的短标识。
- 被流程节点引用的数量。

空状态：

- 当前没有业务构件：提示先在业务组件视图添加构件，并提供返回按钮。
- 当前构件没有实体：实体区显示空状态和“去实体定义”入口。
- 当前构件没有任务：任务区显示空状态和“去任务定义”入口。

交互：

- 返回业务组件：切回业务组件 tab，保留当前构件 ID。
- 构件选择器切换：停留在业务构件 tab，只替换详情内容。
- 点击实体区入口：切换到实体定义 tab，后续可考虑选中对应实体。
- 点击任务区入口：切换到任务定义 tab，并可按当前构件过滤任务。

本轮至少实现切换 tab。是否自动带过滤状态，作为实现阶段的小任务判断；如果当前任务定义已有构件过滤状态，应复用。

### 3.3 任务定义视图

任务定义视图保留现有能力，不在本轮重设 UX。

但它需要和业务构件视图形成入口关系：

- 从业务构件的任务区进入任务定义时，应优先设置 `taskDefConstructId` 为当前构件。
- 从任务定义返回业务构件不是本轮必须项。

### 3.4 实体定义视图

实体定义视图保留现有能力，不在本轮重设 UX。

但它需要和业务构件视图形成入口关系：

- 从业务构件的实体区进入实体定义时，应切换到实体定义 tab。
- 是否自动选中实体，不作为本轮强制要求；如果已有 `runtime.ui.entityId` 机制，可顺手复用。

### 3.5 只读态、编辑态和等待态

构件工作台当前主要是本地文档编辑，不新增远程等待态。

只读态：

- 如果后续文档进入只读模式，业务组件和业务构件视图仍可浏览。
- 新建、编辑、添加构件按钮应禁用或隐藏。当前代码是否有全局只读状态，需要实现前确认。

编辑态：

- 业务组件视图的新建/编辑继续使用现有抽屉。
- 业务构件视图的编辑构件也复用现有构件抽屉。

错误态：

- 当前构件 ID 指向不存在构件时，回落到第一个构件。
- 没有任何构件时，显示空状态，不报错。

## 4. 详细模块设计

### 4.1 `ComponentWorkbenchComponent`

职责：

- 管理构件工作台三级 tab。
- 管理当前构件 UI 状态。
- 提供组件、构件、实体、任务定义查询方法。
- 承载业务组件总览和业务构件详情两个视图。

不负责：

- 不负责实体定义编辑细节。
- 不负责任务定义编辑细节。
- 不负责应用服务管理。

新增或调整的方法：

```ts
switchTab(tab: ComponentTab): void
openBusinessConstruct(construct: LegacyConstruct): void
returnToBusinessComponents(): void
selectedConstruct(): LegacyConstruct | null
ensureSelectedConstruct(): LegacyConstruct | null
componentForConstruct(construct): LegacyComp | null
openTaskDefinitionsForConstruct(construct): void
openEntitiesForConstruct(construct): void
```

边界细节：

- `switchTab('businessConstruct')` 时必须保证有当前构件。
- 从旧 UI 状态恢复到不存在的 tab 时，回落到 `businessComponent`。
- 删除构件时要修正当前构件 ID。

### 4.2 模板结构

建议把模板先在当前文件内分区，不立即拆新组件，避免一次重构过大。

后续如果继续膨胀，再拆：

- `BusinessComponentOverviewComponent`
- `BusinessConstructDetailComponent`

本轮可以先通过清晰的 HTML 分区和 SCSS 分区控制复杂度。

### 4.3 样式结构

样式继续放在：

`frontend-angular/src/app/workbenches/component/component-workbench.scss`

新增样式分区：

- `.business-component-view`
- `.business-component-grid`
- `.business-component-card`
- `.business-construct-list`
- `.business-construct-view`
- `.business-construct-summary`
- `.business-construct-assets`
- `.construct-entity-list`
- `.construct-task-list`

视觉原则：

- 业务组件视图要轻，不出现大面积表格。
- 业务构件视图要清楚分区，实体和任务并列，不混排。
- 卡片圆角保持 8px 左右，和现有工作台风格一致。
- 不使用营销式大 hero，不使用装饰性背景。

### 4.4 数据兼容

构件归属组件：

```ts
construct.businessComponentUid
```

实体归属构件：

```ts
entity.businessConstructUid
entity.businessConstructUids
```

任务归属构件：

```ts
taskDefinition.constructUid
```

不新增字段。

### 4.5 当前代码需要修正的历史边界

当前 `ComponentTab` 仍包含：

```ts
'service' | 'orchestration'
```

但应用服务属于应用工作台，不应继续出现在构件工作台的用户入口中。

实现阶段需要决定：

- 若模板没有使用这些 tab，则从类型和无用方法里移除。
- 若某些方法仍被测试或历史入口引用，则先做兼容映射，后续再清理。

## 5. 用例、测试和验收

### 5.1 组件测试

需要覆盖：

1. 构件工作台显示四个三级 tab：业务组件、业务构件、任务定义、实体定义。
2. 原“组件构件”tab 不再出现。
3. 业务组件视图渲染组件卡片和构件列表。
4. 业务组件视图不直接展示实体名和任务名，只展示数量。
5. 点击构件项后切到业务构件视图。
6. 业务构件视图显示构件基础信息、关联实体、关联任务。
7. 直接切到业务构件且未选择构件时，回落到第一个构件。
8. 返回业务组件后保留当前构件上下文。
9. 从业务构件进入任务定义时，任务定义按当前构件过滤。
10. 没有构件时显示空状态。

### 5.2 浏览器验证

实现后需要在本地页面验证：

- 进入构件工作台。
- 查看业务组件总览。
- 点击构件进入业务构件详情。
- 返回组件视图。
- 切到任务定义和实体定义，确认原能力仍可进入。

### 5.3 构建验证

实现后运行：

```powershell
cd C:\Users\Administrator\Desktop\project\blm\frontend-angular
npm.cmd test
npm.cmd run build
```

构建会刷新根目录 `app/` 产物，提交前需要一并检查。

### 5.4 剩余风险

当前模板和 TS 文件已经比较大。第一轮实现可以不拆子组件，但如果继续叠加复杂编辑能力，应拆出业务组件总览和业务构件详情两个子组件。

当前代码里有历史应用服务/编排方法。若这轮只移除入口、不清理方法，代码仍会有历史包袱；若直接清理，需要额外测试确认没有隐藏入口依赖。

实体和任务的“跳转后自动选中/过滤”依赖现有 UI 状态。任务定义过滤当前已有构件过滤状态，应该复用；实体定义是否能稳定选中实体，需要实现时确认。
