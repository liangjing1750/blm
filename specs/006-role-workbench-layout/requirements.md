# Requirements

## 背景

BLM 当前已经具备全景、流程、角色、实体、任务定义、业务组件、业务构件等模型，但界面入口仍偏“功能集合”。多个角色同时工作时，用户不容易判断自己应该在哪一层补内容，也不容易看出下一棒交给谁。

本轮目标是把已有能力组织成更直观的工作台入口，让项目负责人、产品经理、前端开发、后端开发、应用编排者能沿着自上而下链路协作。

## 目标

- 主导航显式呈现四层工作台：全景工作台、流程工作台、构件工作台、应用编排。
- 每个工作台用界面文案说明对应角色和工作边界。
- 复用现有数据模型，不新增后端核心集合。
- 为后续“概念实体 / 实体设计 / 应用服务场景 / 服务目录”留出入口或文案位置。

## 非目标

- 本轮不实现 AI 助手能力增强。
- 本轮不做权限控制或角色登录。
- 本轮不改 JSON 主模型结构。
- 本轮不实现真实服务目录、部署架构或接口编排引擎。

## 用户旅程

### Journey J006-01: 角色按工作台进入建模

```gherkin
Scenario: 项目团队从主导航识别四层工作台
  Given 用户打开 BLM 文档编辑页
  When 用户查看顶部主导航
  Then 应看到“全景工作台”“流程工作台”“构件工作台”“应用编排”“预览导出”
  And 不应再把主入口命名为“业务架构”“业务域”“业务组件”“应用架构”
```

### Journey J006-02: 产品经理只承担概念实体

```gherkin
Scenario: 产品经理在流程工作台看到实体边界提示
  Given 产品经理进入流程工作台
  When 查看流程节点、表单和实体相关说明
  Then 页面应提示产品经理只维护概念实体名称和表单关联
  And 实体字段、状态、关系应归入构件工作台的开发者职责
```

## 验收标准

- 静态前端测试覆盖主导航新名称和旧名称退场。
- 静态前端测试覆盖“概念实体”和“应用服务场景”等关键承接术语。
- `python -m unittest tests.test_frontend_structure` 通过。
- 至少运行一次前端片段检查，确保 HTML/JS 片段没有明显破损。
