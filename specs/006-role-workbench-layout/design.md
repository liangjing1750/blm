# Design

## 概览

本轮采用“重排入口，少改模型”的方案。主导航从抽象架构名词改为角色可理解的工作台：

- 全景工作台：项目负责人 + 产品经理，维护战略占位、价值流矩阵、业务组件地图、术语角色。
- 流程工作台：产品经理，维护阶段、流程、节点、用户步骤、表单、规则、概念实体。
- 构件工作台：后端开发 + 前端开发，维护实体设计、任务定义、业务构件、服务目录占位。
- 应用编排：应用编排者 + 前后端开发，维护前端接口需求、应用服务场景、后端任务链路、技术承接清单。

## 核心对象

继续复用现有对象：

- `panorama / stages`：支撑全景工作台。
- `processes / nodes / userSteps / forms / rules`：支撑流程工作台。
- `entities / relations / state_transitions`：支撑构件工作台里的实体设计。
- `taskDefinitions / businessConstructs / businessComponents`：支撑构件设计和资产治理。

暂不新增独立 `services` 或 `interfaces` 集合。服务目录、应用服务场景、部署架构先以界面占位和现有 `taskDefinitions[].target` 汇总承接。

## 流程与数据

```text
全景工作台
  -> 定战略、价值流、业务域、业务组件

流程工作台
  -> 拆阶段、流程、节点、角色、表单、概念实体

构件工作台
  -> 细化实体字段/状态/关系，沉淀任务定义和业务构件

应用编排
  -> 页面动作 -> 应用服务场景 -> 构件任务链路 -> 技术承接
```

编排分三层：

- 业务流程编排：流程节点之间的责任流转，留在流程工作台。
- 应用服务编排：一个前端动作背后的构件任务链路，放在应用编排。
- 技术运行编排：服务、数据库、消息、外部系统和部署，先作为占位。

## 关键决策

- 不把“流程节点 = 后端任务链路”作为硬规则。流程节点是业务责任单元。
- 不让产品经理维护实体字段、状态、关系。产品经理只创建概念实体名称和表单关联。
- 不把前端按钮直接称为后端 API。先使用“前端接口需求 / 应用服务场景”作为业务到技术的过渡层。
- 不改后端数据模型，先用导航、文案、汇总视图完成职责分隔。

## 风险与扩展点

- 仅改入口和文案不能完全解决深层模型混用，后续可能需要新增实体成熟度字段。
- 服务目录和应用服务场景如果继续深化，可能需要独立集合，但应等界面语义稳定后再加。
- 现有测试多为静态断言，后续应补一条浏览器 E2E 验证主导航和工作台说明可见。
