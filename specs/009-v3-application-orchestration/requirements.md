# Requirements

## 背景

BLM 前端已经基本迁移到 Angular，旧功能复刻度较高，下一阶段要把 V3.0 的重点从“工作台边界整理”推进到“构件能力 + 应用编排”。本规格承接 `specs/007-blm-v3-workbench-planning`，聚焦流程应用平台对接：BLM 产出可读、可审计、可迁移的 JSON，流程应用平台也通过配置 JSON 描述运行结构，但运行时承载了更多 FSM、接口、事件溯源、查询服务和领域服务细节。

本轮设计不把 BLM 变成流程运行引擎，也不把 BLM 变成低代码平台。它要先帮助团队把“应用服务如何编排构件任务”定义清楚，再为后续 Agent 生成代码提供稳定输入。

## 已确认设计前提

- 构件任务首先是 BLM 中的抽象任务，用来表达“可生成、可承接、可复用的业务能力”。它可以映射到聚合根方法、领域服务方法、HTTP 调用、查询服务或 Agent 生成物，但不被任何一种运行时绑定。
- 前端接口需求和应用服务暂不拆成两个概念。统一使用“应用服务”，表示无状态接入服务对外暴露的 HTTP 接口，同时承接前端页面动作和后端任务编排。
- 变量只存在于一次应用服务编排上下文中。不做全局变量。变量来源包括接口入参、上下文、步骤输出、常量和返回组装。

## 产品目标

- 让构件工作台从“实体、任务、构件资产目录”升级为“可承接运行时的业务能力定义”。
- 让应用编排工作台能定义一个应用服务接口，并在该接口内部编排多个构件任务。
- 让应用编排具备最小参数变量设计能力，能表达接口入参、上下文变量、步骤输入映射、步骤输出绑定和返回结果组装。
- 让流程节点可以引用应用服务，但不把流程节点等同于应用接口。
- 让 BLM 的 JSON 成为 Agent 生成接入服务、领域服务调用、查询服务调用或编排代码的输入，而不是直接承担运行时执行。

## 非目标

- 不实现流程运行引擎。
- 不实现编排运行时。
- 不实现 Agent 集成。
- 不做代码生成。
- 不做复杂条件分支、循环、并行、补偿事务。
- 不做全局变量或跨应用服务变量池。
- 不引入 BPMN 网关、泳道或复杂流程语义。
- 不把应用服务、构件任务和流程节点强行建成上下级关系。

## 关键概念

### 流程节点

流程节点表达业务责任单元，说明某个角色在某个责任边界内连续做什么。流程节点可以触发或引用应用服务，但流程节点不是应用服务，也不是运行时接口。

### 应用服务

应用服务是无状态接入服务对外暴露的 HTTP 接口。它同时承接前端页面动作、流程节点动作和后端构件任务编排。

第一版应用服务至少表达：

- 名称、方法、路径和说明。
- 关联流程节点或页面操作入口。
- 请求参数和返回参数。
- 编排步骤。
- 编排上下文变量。
- 返回映射。

### 构件任务

构件任务是业务构件对外暴露的抽象能力。它不是某一种技术方法的直接别名，而是 BLM 用来沉淀“这个构件能做什么、需要什么输入、产生什么输出、如何被技术承接”的建模对象。

第一版构件任务至少表达：

- 所属构件。
- 任务名称和任务意图。
- 输入参数。
- 输出参数。
- 技术承接说明。

### 技术承接

技术承接从原来的流程节点任务中前移到构件任务。它说明构件任务未来可能落到哪里，例如：

- FSM 内嵌领域服务 Jar。
- 聚合根方法。
- 查询服务 SQL + HTTP。
- 外部 HTTP 服务。
- Agent 生成代码。
- 人工实现。

技术承接不要求第一版能执行，只要求能让后端研发和 Agent 明白实现方向。

### 编排变量

编排变量只在一次应用服务调用内有效。变量分为：

- `request`：应用服务请求参数。
- `context`：调用上下文，例如当前用户、租户、业务域、操作时间。
- `step`：某个编排步骤输出。
- `const`：应用服务内局部常量。
- `return`：最终返回结果组装。

## 用户旅程

### Journey J009-01: 后端研发定义构件任务

```gherkin
Scenario: 后端研发在构件工作台定义可承接运行时的构件任务
  Given 后端研发进入构件工作台
  And 已存在业务构件“入库预约”
  When 后端研发新增构件任务“保存入库预约”
  Then 应能填写任务意图、输入参数、输出参数和技术承接说明
  And 该任务不应直接绑定到某一个流程节点
```

### Journey J009-02: 技术经理定义应用服务

```gherkin
Scenario: 技术经理为页面提交动作定义应用服务
  Given 技术经理进入应用编排工作台
  When 新增应用服务“提交入库预约”
  Then 应能维护 HTTP 方法、路径、请求参数、返回参数和关联操作入口
  And 应能把该应用服务关联到流程节点或页面动作
```

### Journey J009-03: 技术经理编排多个构件任务

```gherkin
Scenario: 技术经理在一个应用服务下编排多个构件任务
  Given 应用服务“提交入库预约”已经存在
  And 构件工作台中存在“校验仓库状态”“校验品种准入”“保存入库预约”“生成待办”四个构件任务
  When 技术经理编辑该应用服务的编排
  Then 应能按顺序选择构件任务作为编排步骤
  And 应能为每一步维护输入映射和输出绑定
```

### Journey J009-04: 技术经理设计参数传递

```gherkin
Scenario: 技术经理把前一步输出传给后一步输入
  Given “保存入库预约”步骤输出 `reservationId`
  When 技术经理配置“生成待办”步骤输入
  Then 应能把 `step.saveReservation.reservationId` 映射到 `reservationId`
  And 该变量只在“提交入库预约”应用服务编排内可见
```

### Journey J009-05: 产品或流程人员回看应用服务来源

```gherkin
Scenario: 流程节点回看关联应用服务
  Given 产品经理进入流程工作台
  When 查看“客户提交入库预约”流程节点
  Then 应能看到该节点引用了应用服务“提交入库预约”
  And 不应要求产品经理维护构件任务参数或技术承接
```

## 最小业务样例

第一版设计用“提交入库预约”验证概念闭环：

```text
流程节点：客户提交入库预约
应用服务：POST /inbound-reservations/submit

应用服务请求：
  warehouseId
  productId
  goodsAmount
  appointmentDate

编排步骤：
  1. 校验仓库状态
  2. 校验品种准入
  3. 保存入库预约
  4. 生成待办
  5. 发布流程事件

变量传递：
  request.warehouseId -> step.checkWarehouse.input.warehouseId
  request.productId -> step.checkProduct.input.productId
  step.saveReservation.output.reservationId -> step.createTodo.input.businessId
  context.operatorId -> step.saveReservation.input.operatorId
  step.saveReservation.output.reservationNo -> return.reservationNo
```

## 验收标准

- 规格文档明确流程节点、应用服务、应用编排、构件任务、技术承接和编排变量的边界。
- `design.md` 给出最小数据结构草案，但不要求本轮直接改代码。
- `tasks.md` 把后续开发拆成可验证的小任务，每个任务能单独验收。
- `status.md` 记录当前只完成设计，不宣称功能已实现。
