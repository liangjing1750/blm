# 主动同步协作改造规格

## 背景

BLM 文档是结构化大 JSON。实时推送完整快照会带来两个问题：

- 大文档在弱网下频繁传输，容易断线、卡顿。
- 其他人同步后，当前页面自动应用远端快照，可能覆盖本地正在编辑的内容或导致光标/界面跳动。

## 目标

1. 数据提交只通过 `Ctrl+S / 立即同步` 触发。
2. WebSocket 只承担在线状态和“有新版本”通知，不推送、不自动应用完整文档。
3. 本地修改只写入本地草稿并显示待同步状态，不自动发送整份文档。
4. 服务端继续使用 `baseSeq` 串行合并，防止旧版本覆盖新版本。
5. 增加多线程并发测试，覆盖多人同一文档同步场景。

## 修改范围

- `app/collab.js`
  - `queueCollabSnapshotSync()`：取消定时自动 flush，只保留本地草稿和待同步状态。
  - `syncCollabImmediatelyFromCommand()`：统一走 HTTP snapshot。
  - `handleCollabMessage()`：远端 `snapshot` 或 `snapshot_notice` 只记录有新版本，不应用文档。
  - `pollCollabOnce()`：发现更新只提示，不拉取并应用完整文档。
  - 保留本地草稿、诊断、在线用户显示。
- `blm_core/collab.py`
  - HTTP snapshot 成功后广播轻量通知，不带完整 `document`。
  - WebSocket snapshot 保留兼容，但广播同样只发通知。
- `tests/test_collab.py`
  - 调整广播断言。
  - 新增多线程并发同步测试。

## UX

- 本地编辑：显示“待同步/本地草稿待同步”。
- 其他人同步：显示“有新版本，按 Ctrl+S/立即同步后合并刷新”。
- 用户只需要理解一个动作：立即同步。

## 验收场景

1. 用户连续编辑 10 秒，未按同步时不发送快照。
2. A 同步后，B 只收到新版本提示，B 当前界面不变。
3. B 按同步后，服务端按 `baseSeq` 合并，返回最新文档。
4. 多线程同时同步不同字段，最终文档保留所有非冲突修改。
5. 多线程同时同步同一字段，服务端串行处理，最终文档合法且 `seq` 连续增长。
