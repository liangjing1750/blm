# Requirements

## 背景

BLM 当前已经具备全景、流程、表单、实体、任务定义、业务组件、业务构件、角色和术语等基础能力。问题不在于完全缺功能，而在于多人协作时边界不清，工具没有充分引导用户按业务架构方法工作。

本规格以 `docs/BLM v3版本思考.html` 为方案基线，目标是把 BLM v3 逐步整理成业务架构建模工具。它服务业务负责人，同时让产品经理、技术经理、前端研发和后端研发在各自工作台内协作。

## 产品定位

- BLM v3 是业务架构建模工具。
- 核心价值是把业务负责人对业务的理解结构化，形成价值流、业务域、阶段、流程、角色、表单、概念实体和业务组件。
- 上游承接战略、目标、业务规划和管理口径。
- 下游衔接流程应用平台、表单配置、接口设计和任务实现。
- 不做流程运行引擎，不做低代码平台，不做单纯接口管理工具。

## 目标

- 用一个主要工作台约束一个角色的主要工作范围。
- 全景工作台把战略设计、价值流矩阵和业务组件放在一个总览关系中，同时保留分区维护。
- 流程工作台把概念实体贴着流程、用户步骤、表单、原型说明展示和维护。
- 构件工作台以弱参考方式查看流程产物。第一版中，概念实体与逻辑实体先按一一对应处理，减少数据模型变动。
- 应用编排工作台以页面/原型引用、前端接口需求、接口后的后端任务链路为主线。
- 优先复用现有数据模型和现有界面能力，新增概念先用界面分组、标签、说明和弱参考表达。

## 非目标

- 不在本轮引入新的后端核心模型重构。
- 不实现权限系统或角色登录隔离。
- 不实现流程运行引擎、低代码运行能力或部署架构。
- 不把 AI 助手作为第一优先级开发内容。
- 不把“应用服务场景”“技术承接”“服务目录”“交互动作”作为独立工作台入口。

## 角色与主工作台

| 角色 | 主要工作台 | 主要责任 |
|---|---|---|
| 总负责人 | 全景工作台 | 确定目标、范围、业务边界和优先级 |
| 产品经理 | 流程工作台 | 维护阶段、流程、用户步骤、表单、概念实体 |
| 技术经理，兼应用编排者 | 应用编排工作台 | 组织前端接口需求和后端任务链路 |
| 前端研发 | 应用编排工作台 | 根据原型、页面说明和表单整理前端接口需求 |
| 后端研发 | 构件工作台 | 维护逻辑实体、任务定义和业务构件 |

## 关键业务规则

- 概念实体是业务名词，产品经理只维护名称、业务含义和来源说明。
- 逻辑实体更接近表结构，由后端研发维护字段、状态、关系和生命周期。
- 第一版中，一个概念实体默认对应一个逻辑实体。
- 界面不等于表单。当前先用原型附件、页面说明和操作入口表达界面层。
- 构件工作台可以参考流程产物，但这种参考是弱关联，主要用于说明来源和形成记录。
- 前端接口需求是应用调用入口，一个接口后面可以编排一组构件任务。

## 用户旅程

### Journey J007-01: 总负责人查看全景关系

```gherkin
Scenario: 总负责人从一个工作台查看战略、价值矩阵和业务组件
  Given 用户打开 BLM v3
  When 用户进入全景工作台
  Then 应能看到战略设计、价值流矩阵、业务组件三部分之间的关系
  And 应能分区维护三部分内容
```

### Journey J007-02: 产品经理维护概念实体

```gherkin
Scenario: 产品经理在流程工作台维护概念实体
  Given 产品经理进入流程工作台
  When 查看流程节点、用户步骤、表单和原型说明
  Then 应能为相关业务对象维护概念实体名称和业务含义
  And 不应被要求维护字段类型、状态机或表关系
```

### Journey J007-03: 后端研发参考流程产物设计构件

```gherkin
Scenario: 后端研发在构件工作台查看流程参考
  Given 后端研发进入构件工作台
  When 设计逻辑实体、任务定义和业务构件
  Then 应能看到概念实体、用户步骤、表单、业务规则等流程参考
  And 系统应按一一对应关系呈现概念实体与逻辑实体
```

### Journey J007-04: 技术经理组织接口到任务链路

```gherkin
Scenario: 技术经理在应用编排工作台组织接口需求
  Given 技术经理进入应用编排工作台
  When 查看页面、原型、用户步骤和操作入口
  Then 应能维护前端接口需求
  And 应能表达接口后面调用的一组后端任务
```

## 验收标准

- 每个开发任务开始前，都有明确修改范围、测试方式和验收标准，并经用户确认。
- 每个开发任务优先补测试或静态验证，再做最小实现。
- 当前任务完成后，更新本规格的 `tasks.md` 和 `status.md`。
- 用户验收通过后，才提交代码并进入下一任务。
