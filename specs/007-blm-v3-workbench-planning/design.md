# Design

## 设计原则

1. 先界面分层，后模型扩展。
2. 先弱参考，后强关系。
3. 先复用现有能力，后新增能力。
4. 一个角色只有一个主要工作台，其他工作台只做输入、评审或协同。
5. 前端按工作台隔离，上层到下层单向依赖，同层工作台之间不直接依赖。

## 前端目标架构

```text
core
  app shell / action / DOM 基础能力

shared
  UI helper / document query / model ref

workbenches
  panorama / process / component / orchestration / entity / knowledge

legacy
  尚未完全迁出的旧实现，后续逐步清空
```

依赖规则：

- `workbenches/*` 可以依赖 `shared` 和 `core`。
- `shared` 不依赖任何工作台。
- 同层工作台之间不直接依赖。
- 视图模型不直接访问 DOM。
- 工作台之间需要跳转时，通过 `AppActions` 发起统一动作。

当前迁移策略：

- 全景工作台先拆出独立视图模型和渲染模块。
- 应用编排台先拆出独立工作台模块。
- 流程、构件、实体先通过 facade 隔离入口，后续在对应工作台内继续收敛。
- 继续使用普通 `<script>` 加载，暂不切换 ES Modules，降低一次性重构风险。

## 工作台结构

```text
全景工作台
  战略设计 / 价值流矩阵 / 业务组件

流程工作台
  阶段 / 流程 / 用户步骤 / 表单 / 原型与界面参考 / 概念实体

构件工作台
  流程参考 / 逻辑实体设计 / 任务定义 / 构件管理

应用编排工作台
  页面与原型引用 / 前端接口需求 / 接口后的后端任务链路
```

## 全景工作台

全景工作台要把战略设计、价值流矩阵和业务组件放在同一张业务地图中，但不要求在一个复杂画布里维护所有内容。

推荐结构：

- 总览区：展示三者关系。
- 战略分区：维护愿景、价值观、目标。
- 矩阵分区：维护价值流、业务域、阶段卡片。
- 组件分区：维护业务组件、覆盖流程、资产覆盖情况。

实现优先级：

- 先调整现有展示和说明。
- 再考虑总览图或关系视图。
- 不先新增复杂编辑器。

## 流程工作台

流程工作台面向产品经理，重点是业务交互，不是技术设计。

概念实体展示建议：

- 在流程节点或用户步骤详情中显示相关概念实体。
- 在表单区域显示“该表单涉及的概念实体”。
- 在右侧或底部提供概念实体清单，展示来源、业务含义、是否已被构件工作台参考。

界面层处理：

- 界面不等于表单。
- 当前不新增完整页面模型。
- 先复用原型附件、页面说明和操作入口表达界面层。
- 如果后续页面模型稳定，再考虑独立建模。

## 构件工作台

构件工作台面向后端研发，重点是逻辑实体、任务定义和业务构件。

承接方式采用弱参考：

- 可以看到流程工作台中的概念实体、用户步骤、表单、业务规则。
- 可以手工记录某个逻辑实体或任务参考了哪些流程产物。
- 不要求建立强制关系。
- 第一版按概念实体与逻辑实体一一对应展示，降低实现和迁移成本。

实体边界：

- 概念实体是业务名词。
- 逻辑实体更接近表结构。
- 第一版中，一个概念实体默认对应一个逻辑实体。
- 后续如果一对多需求稳定，再单独扩展模型和界面。

## 应用编排工作台

应用编排工作台面向技术经理和前端研发，重点是接口需求和任务链路。

建议主线：

```text
页面或原型
  -> 用户步骤
  -> 操作入口
  -> 前端接口需求
  -> 接口后的后端任务链路
```

说明：

- 页面是界面承载。
- 用户步骤是业务动作。
- 操作入口通常是按钮、菜单、链接或自动触发点。
- 前端接口需求是应用调用入口。
- 后端任务链路引用构件工作台中的任务定义。

## 数据模型策略

本规格不先要求后端模型大改。优先策略：

- 用现有 `entities` 区分概念实体和逻辑实体时，先考虑界面标签或派生展示。
- 用现有表单、流程节点、用户步骤和附件表达来源。
- 用现有 `taskDefinitions` 表达任务定义。
- 前端接口需求和后端任务链路如果现有模型不足，先做界面占位或轻量结构，再进入单独任务确认。

## 测试策略

- UI 结构类任务：先写静态结构测试，确认关键入口、文案、旧概念退场。
- 交互类任务：先写用户旅程或浏览器验收路径，再实现。
- 数据转换类任务：先写单元测试，覆盖现有数据兼容和空状态。
- 每个任务只验证本任务范围，并跑相关回归。
