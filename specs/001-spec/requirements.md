# Requirements

## 背景

BLM 当前以工作区文档包为核心，前端通过 HTTP 加载、保存、比对和合并文档。系统已经具备 revision 乐观锁、历史快照、合并能力，但多人协作仍偏“离线分支/复制文档/保存时合并”的模式。

团队正式推广后，一个业务模型会被产品经理、流程编排、前端、后端同时维护。长期看，BLM 应从“文件式协作”升级为“在线工作稿 + 变更记录 + 版本快照”的协作模型，减少分支和人工合并带来的理解成本。

## 目标

- 引入实时协作基础设施，让多个浏览器可以加入同一文档会话。
- 服务端维护文档会话、在线用户、递增 `seq`、追加式变更日志。
- 第一阶段保留现有 HTTP 保存能力，避免一次性推翻当前稳定链路。
- 为后续自动保存、字段级 LWW、命名版本、只读快照和定位链接打基础。

## 非目标

- 第一阶段不实现完整 CRDT/OT。
- 第一阶段不替换所有前端编辑控件为实时字段变更。
- 第一阶段不取消现有保存、历史、合并功能。
- 第一阶段不做 Confluence API 集成。
- 第一阶段不做完整权限体系。

## 需求

- 用户打开文档后，系统可以为该文档建立协作会话。
- 多个用户加入同一文档时，服务端返回同一份当前文档、当前 `seq` 和在线用户列表。
- 前端可以显示“当前在线协作者”的轻量提示。
- 前端需要提供基础用户账号设置，用于显示“谁在线、谁刚更新”；该账号不做权限控制，只作为协作身份。
- 同一浏览器打开多个页面时应复用同一用户身份，但每个页面仍是独立连接；在线人数按用户去重，连接数作为辅助信息展示。
- 服务端可以接收字段级变更事件，按文档追加到 `collab/changelog.jsonl`。
- 服务端对每条变更分配严格递增的 `seq`，并广播给同文档其他会话。
- 客户端收到远程变更后，能够更新内存中的文档对象，并触发重新渲染。
- 服务端提供降级能力：如果 WebSocket 不可用，现有 HTTP 打开和保存仍然可用。

## 验收标准

- 两个浏览器同时打开同一文档，能看到在线人数或在线用户变化。
- 一个浏览器发送协作变更，服务端返回 `ack`，另一个浏览器能收到同一条变更。
- 变更日志中能看到按 `seq` 递增的 JSONL 记录。
- 刷新文档后，现有 HTTP 加载和保存不受影响。
- 旧的保存、历史快照、合并接口测试保持通过。

## 产品打磨补充需求

- 自动保存存在后，不再用黄色横幅反复提醒“未保存”，避免页面抖动；顶部只保留轻量同步状态。
- 文档支持“团队空间”和“标签”元数据，用于工作区打开弹窗分组管理。
- 历史记录入口放到顶部一级操作区，统一查看“归档版本”和近期历史。
- 支持右键复制定位点链接，至少覆盖当前视图、流程、节点、实体和只读版本。
- 自动保存产生的协作日志需要可控，按条数或体积进行合并压缩，避免长期保存点膨胀。
- 在线协作验收应覆盖流程六级模型的代表性元素：价值流/业务域、阶段、流程、节点、步骤/任务、表单/实体。
