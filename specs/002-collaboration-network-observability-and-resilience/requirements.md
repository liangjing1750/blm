# Requirements

## 背景

BLM 部署在内网服务器后，同团队使用正常，其他团队频繁断线。由于开发环境和实际网络环境不一致，现阶段无法直接复现跨网段策略、代理、防火墙或弱网问题。

当前主要缺口：

- 服务端日志不足，无法判断 HTTP、WebSocket、自动保存、协作同步分别卡在哪里。
- 协作状态对用户暴露过多内部概念，弱网下容易频繁提示。
- 大文档实时同步成本高，网络差时更容易断线或超时。
- 缺少管理/诊断入口，无法快速收集服务器状态、在线连接、最近错误和日志。

## 目标

- 增强服务端可观测性，能定位跨网段断线问题。
- 保留当前 snapshot 协作架构，不立即重写为完整 changelog/CRDT。
- 在弱网下尽量保持可用：连接可诊断、断线可恢复、同步不轻易覆盖他人更新。
- 增加前端连接诊断能力，让用户能截图或复制诊断信息。
- 增加管理端/监控端基础能力，方便管理员查看服务状态和协作连接。

## 非目标

- 本轮不引入用户权限体系。
- 本轮不实现完整实时文本 CRDT。
- 本轮不把全部业务模型编辑改造成细粒度 change 事件。
- 管理端优先只读监控，不提供高风险操作。

## 需求

### R1 日志与诊断

- 服务启动时记录监听地址、端口、workspace、Python 版本和日志目录。
- HTTP 请求记录客户端 IP、方法、路径、状态码、耗时。
- WebSocket 记录 join、disconnect、error、ping/pong、snapshot、rebase、autosave。
- 关键日志按天或大小滚动，避免无限增长。
- 前端能展示当前连接状态、seq、最近错误、在线用户和最近断线时间。

### R2 协作底线保护

- 服务端是 snapshot 同步的最终裁判。
- 客户端提交旧 baseSeq 时，服务端不能直接覆盖当前文档。
- 服务端能基于近期 seq 快照做轻量三方合并。
- base 太旧无法合并时，返回明确错误，提示重新加载或立即同步失败。

### R3 弱网体验

- 远端更新不应频繁弹横幅。
- 顶栏用轻状态表达：已同步、同步中、有更新待同步、连接中断。
- 断线时本地草稿保留，并提示不要关闭页面。
- 大文档同步要减少无意义发送，尽量基于 hash 或防抖避免重复 snapshot。

### R4 HTTP 降级

- WebSocket 不可用时，前端可进入轮询模式。
- 轮询能拉取当前文档 seq 和最新 snapshot。
- 立即同步可通过 HTTP POST 提交 snapshot。
- 降级模式实时性降低，但基本编辑和同步可用。

### R5 管理端

- 管理端独立端口启动。
- 展示服务状态、文档状态、协作连接、最近错误和日志摘要。
- 支持下载诊断包。
- 默认只读，避免误操作。

## 验收标准

- 自动测试覆盖服务端旧 baseSeq 不覆盖新版本。
- 自动测试覆盖远端更新只显示轻状态，不频繁弹横幅。
- 自动测试覆盖连接诊断信息可展示。
- 管理端健康接口可返回服务状态。
- 日志文件在本地运行后可生成，包含 HTTP 和协作关键事件。
