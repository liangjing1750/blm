# 需求梳理：CSS/SCSS 统一规范

更新日期：2026-06-25

## 1. 问题现状

### 1.1 数据事实

| 指标 | 数值 |
|------|------|
| `styles.scss` 总行数 | 9,911 |
| 已确认为 still-used 的选择器 | 628 |
| global-shell-or-rendered-content（壳层/弹窗/渲染内容） | 213 |
| suspected-dead（疑似废弃） | 961 |
| 共享样式层文件数 | 4（_base / _buttons / _forms / _modals，共 190 行） |
| 组件级 SCSS 文件数 | ~37 |
| angular.json 中注册的全局样式入口 | 仅 `src/styles.scss` 一个 |

### 1.2 核心问题

1. **无分级管理体系**：没有明确定义「项目级 → 模块级 → 组件级」三层边界，导致样式随意堆放。
2. **`styles.scss` 是 9900 行巨石**：壳层样式、工作台样式、废弃样式混在一起，无人敢删。
3. **961 条疑似废弃选择器**：未经验证也未删除，持续增加构建体积和维护负担。
4. **组件样式文件命名不一致**：
   - `.scss` 和 `.css` 混用（`app.css`, `workbench-section.css`）
   - 文件名有 `*-workbench.scss`、`*-workbench.component.scss`、`*-layout.scss` 等多种模式
5. **部分组件 SCSS 超预算**：7 个文件超过 4kB style budget。
6. **无强制检测机制**：没有 lint 规则或检查脚本防止样式回流到全局文件。

### 1.3 不属于本轮

- 不迁移具体工作台样式（那是后续迭代任务）
- 不修改 `styles.scss` 中 628 条 still-used 选择器的视觉表现
- 不改变现有 CSS 变量体系
- 不引入 Tailwind/Bootstrap 等第三方 CSS 框架

## 2. 功能归属

- **工作台**：跨工作台（基础设施）
- **能力类型**：新能力 — 样式工程规范
- **旧版是否已有**：旧版无此规范，旧版 `app/style.css` 同样是巨石文件

## 3. 输入与输出

### 输入
- 当前 `styles.scss`（9911 行）
- `docs/refactor/styles-classification.csv`（1803 行分类数据）
- 现有 37 个组件 SCSS 文件
- `angular.json` 构建配置

### 输出
- 三级样式管理规范文档
- 目录结构约定
- 命名约定
- 导入/依赖规则
- 废弃样式清理流程和脚本
- CI/检查脚本

## 4. 界面状态（管理面）

| 状态 | 描述 |
|------|------|
| 规范态 | 规范文档可供开发人员查阅 |
| 检测态 | 检查脚本可运行，输出违规报告 |
| 迁移态 | 样式按规范逐步迁移到正确层级 |
| 清理态 | suspected-dead 选择器经确认后删除 |

## 5. 用户旅程（验收旅程）

1. 开发者新增组件 → 知道样式应该写在哪里
2. 开发者修改公共样式 → 知道应该改 shared/ 哪个文件
3. CI 或 pre-commit → 可检测新增的全局样式污染
4. 维护者 → 可按检查脚本输出定位和清理废弃样式

## 6. 涉及协作同步

否 — 纯前端工程规范，不涉及运行时同步。

## 7. 验收标准

- 存在书面规范，定义了项目级/模块级/组件级三层边界
- shared/ 目录有明确的「可以放什么、不能放什么」说明
- 组件 SCSS 文件命名统一（全部使用 `.scss`，命名模式一致）
- 存在检查脚本可以统计全局样式行数和分类
- 疑似废弃样式有清理路径（至少工具能列出待清理清单）
- `npm.cmd run build` 通过
- `npm.cmd test -- --watch=false` 通过
