# 协作数据安全改造规格

## 背景

弱网或大文档场景下，浏览器可能短暂断开协作连接。此时用户继续编辑，如果随后收到远端快照或用落后的版本提交，存在两类风险：

- 自己的未同步修改被远端内容覆盖。
- 自己基于旧版本提交时覆盖别人已经同步的修改。

## 目标

1. 浏览器本地必须有草稿兜底，断线、刷新或同步失败后能恢复自己的未同步内容。
2. 服务端必须以 `baseSeq` 做串行保护，旧版本提交不能直接覆盖当前文档。
3. 远端更新到达时，如果本地正在编辑或有待同步内容，只提示并暂存，不主动重绘编辑区。
4. 诊断信息必须能显示草稿、待同步、远端更新和序列号状态，便于弱网排查。

## 非目标

- 不实现字符级 CRDT/OT。
- 不引入权限或用户登录权限模型。
- 不把协作历史作为完整审计日志。

## 关键规则

- 每次本地修改进入自动同步队列前，先写入浏览器本地草稿。
- WebSocket 不可用时，草稿保留，页面显示重连恢复状态，并允许立即同步走 HTTP 降级。
- 服务端收到 `baseSeq < currentSeq` 的快照时，基于 `baseSeq` 对应快照进行三方合并。
- 如果 `baseSeq` 太旧，服务端拒绝覆盖，并将客户端提交内容保存为冲突留痕文件。
- 同步成功并得到服务端确认后，清除对应本地草稿。

## 验收场景

1. A 修改并同步，B 基于旧版本同步，服务端保留 A 的修改并合并 B 的修改。
2. B 断线后继续编辑，刷新或重连后能看到本地草稿提示，并可恢复同步。
3. 本地有未同步内容时收到远端更新，不立即覆盖当前编辑界面。
4. 诊断弹窗能看到本地草稿状态、草稿时间和同步序列号。
